# ORGY 核心架构与协作范式

**O**pen-ended **R**esilient **G**enerative **Y**ard

**Status:** 草案 `0.2.0`

**Date:** 2026-11-14

---

## 摘要

ORGY 是一个面向通用软件与异构硬件开发的多智能体协同编排引擎。它不封装大模型 API，而是以操作系统级原语（子进程、文件系统、Git、沙箱）驱动用户本地已经配置好登录态与环境变量的第三方终端 AI 工具（如 `codex`、`dsh`），把不同能力、不同成本、不同响应速度的模型组织成一条可验证的研发流水线。

本草案给出的设计分为三层：

- **执行层**：以一次性 headless 子进程为主路径，把交互式终端（PTY）降级为诊断与人工处理的通道；
- **状态层**：磁盘上的规范层与运行时层冷热分离，已接受状态只有一个写者，人类编辑独立提案；
- **规范层**：在人类可读的 Markdown 中嵌入机器可解析的条目，由条目依赖关系计算增量重算范围。

贯穿三层的是十条**核心状态不变量**（§2.4）。它们是本架构的地基，每一条都附带客观的检测方式——不可检测的约定不纳入不变量。

建议的阅读顺序：§2（原则与不变量）→ §3.2（三层判据）→ §3.3（状态层）→ §3.6（语义化规范层与增量重算）→ §4（协同拓扑）。

## 术语表

| 术语 | 含义 |
| --- | --- |
| **Supervisor** | 编排进程。它是已接受规范与运行时状态的唯一写者，负责调度、判定与落盘；提案与 Worker 输出另有独立目录 |
| **Worker** | 由 AI 工具进程承担的一次性执行者，无持久状态 |
| **任务（Task）** | 具备明确验收条件的可验证工作单元，通常对应一个最小垂直切片 |
| **会话（Session）** | 工具自身的对话状态，可跨多次进程调用续接 |
| **尝试（Attempt）** | 一次 headless 子进程调用。粒度最细，可随时丢弃 |
| **条目（Entry）** | 规范层中带稳定 ID 的机器可解析单元，如一条假设、一条接口、一个任务定义 |
| **语义投影** | 条目中真正具备约束力的字段子集，用于计算内容哈希 |
| **内容哈希** | 仅覆盖单个条目语义投影的指纹 |
| **有效哈希** | 条目自身内容哈希与其依赖条目有效哈希共同滚动的指纹（§3.6.3） |
| **注入清单** | 派发任务时实际注入 Worker 上下文的条目及其哈希，构成规范读集；源码读取另行记录 |
| **读集 / 写集** | 规范条目、源码与构建输入的依赖集合 / 任务声明可写的路径集合（公开与私有产物之并集） |
| **验证收据（receipt）** | 一次验证的完整凭据：输入、代码、环境摘要与结果 |
| **爆炸半径** | 某条目变更后需要重算或重验的任务集合 |
| **早期截断（early cutoff）** | 按依赖边的摘要与读取边界复用结果；公开接口摘要相同不代表运行时行为相同 |
| **表象层（surface）** | 第三方工具的消息格式、终端渲染等无兼容性承诺的呈现形式 |
| **暂存区（staging）** | 按合并队列构造候选提交并运行完整验证的隔离工作区 |
| **集成单元（integration unit）** | 可独立通过验收的单任务，或显式声明、整体晋升的有界任务组 |

## 1. 项目愿景与问题陈述

### 1.1 定位

ORGY 的目标不是重新实现一个 AI 编程助手，而是解决**已有多个 AI 编程助手之后**的问题：如何让它们并行、可验证、可恢复地协同，并且让人类始终掌握方向。

因此 ORGY 明确站在工具之上而非之下：它不实现推理调用，也不建立自己的长期模型凭证库；启动工具时可使用用户授权的凭证句柄或最小环境，负责编排进程、约束环境、收集产物、执行验证、记录事实。

### 1.2 需要解决的四个问题

1. **工具链割裂**：多个终端窗口各自为战，缺乏上下文同步、文件并发控制与统一的验证闭环。人类的判断散落在多个会话里，无法回溯。
2. **能力与成本错配**：快而廉价的模型容易陷入循环或缺乏全局视角；强而昂贵的模型响应慢、成本高，不适合承担大量样板代码与测试编写。二者的分工需要由系统而非人脑来维持。
3. **进程脆弱性**：第三方 CLI 工具在长任务中可能因网络波动、上下文压缩或终端渲染异常而卡死。任何“等它自己好起来”的策略都不可靠。
4. **需求模糊与过度设计的矛盾**：用户初期目标往往不完整；若让 AI 提前做详尽架构设计，又会产生大量僵化的防御性代码，导致后期难以转向。

### 1.3 由此导出的设计约束

| 问题 | 设计约束 |
| --- | --- |
| 工具链割裂 | 状态必须落盘为可读文本，且只有一个写者 |
| 能力成本错配 | 角色与模型级别必须解耦，且支持按失败类型升级 |
| 进程脆弱 | 执行者必须可随时丢弃，记忆不能驻留内存 |
| 过度设计 | 校验必须由机器完成，人的介入点必须少而关键 |

## 2. 设计原则

### 2.1 状态与执行解耦

借鉴 Erlang/Elixir 的 Actor 模型与监督树（supervision tree）：系统的“记忆”放在磁盘上，“算力”放在可丢弃的进程里。进程崩溃是正常事件，不是需要防御的异常。

在实现这套模型之前，必须先把三个层级分清，否则“容错”会退化为“反复重来”：

| 层级 | 生命周期 | 载体 | 丢弃代价 |
| --- | --- | --- | --- |
| **Task** | 跨多次尝试 | `spec/tasks/<id>.yaml` 与运行时状态 | 高：需要重新规划依赖 |
| **Session** | 跨多次 Attempt | 工具自身的会话存储（如 `codex exec resume`、`dsh --resume`） | 中：丢失模型已建立的理解，重试时需重建上下文 |
| **Attempt** | 单次子进程调用 | 一次性 headless 进程 | 进程可丢弃；终止前后仍需保全磁盘现场与副作用记录 |

由此得到两条操作：

- `restart(process)`：旧进程树确认退出并保存现场后，复用 Task 的固定 CWD 与会话目录；仅在适配器探针确认支持续接、会话可读且上下文仍适用时续接。工作区发生变化时注入变更说明；工具不支持续接或会话损坏时开启新会话。
- `reset(context)`：方向错误、上下文污染或输入失效时开启新会话，注入最新契约与 Supervisor 保存的恢复摘要。是否保留代码现场由显式恢复策略决定，重置会话不等于自动清空代码。

会话定位是否依赖 CWD 是工具与版本相关的能力，不能一概而论。固定 Task 路径降低兼容风险，但不能替代续接探针与输入校验；同一 Task 的 Attempt 始终串行（§3.5）。

把两者混为一谈，会让系统在每次重试时都从零开始理解代码，既昂贵又健壮性更差。

**监督树策略**：

- `one_for_one`（局部自愈）：单个 Worker 卡死或偏离任务时，仅重建该次尝试，不影响同级并行任务。
- `rest_for_one`（级联重置）：规范条目演进后，仅重建**读集中包含受影响条目**的下游任务（§3.6.4）。这里的关键是“仅”，否则级联重置等同于全量重启。

### 2.2 渐进式探索与契约演进

- **最小活体切片（tracer bullet）**：初期禁止复杂抽象与防御性代码，优先用最直白的实现端到端跑通一条可观测链路（例如“串口收到指令 → 点亮 LED → 返回状态”）。目的是尽早暴露目标偏差，而不是尽早完成代码。
- **契约即边界**：模块之间只通过极简的接口契约解耦，使主逻辑与测试/仿真可以真正并行。契约必须**同时是人类可读的散文与机器可解析的条目**（§3.6），否则并行安全性与 mock 自动生成都无从建立。
- **契约双向演进**：底层执行者在接触真实编译器或硬件寄存器时若发现契约存在物理或逻辑矛盾，**不得私自妥协**，而应输出 `contract_friction` 并挂起任务；Supervisor 唤醒架构角色评估并修订契约，再触发受影响下游的级联重置。
- **假设显性化**：用户未说明的需求盲区必须显式记入假设账本（带稳定 ID 与默认值），而不是默默写死在代码里。Worker 必须声明本次实际使用了哪些假设，使“隐含猜测”变成可审计的数据。

### 2.3 正确性不依赖第三方表象

这是本设计最基础的一条原则：

> **正确性只依赖三样东西：进程退出状态、磁盘产物、ORGY 自己的验证器。**
>
> 终端屏幕内容、ANSI 控制序列、JSONL 事件名称、提示符样式，均属于**表象层**，只能用于延迟优化、进度展示、成本统计与故障诊断。

理由：屏幕渲染和事件名称都是第三方工具的实现细节，没有任何兼容性承诺。把系统正确性建立在它们之上，等于把可靠性寄托在别人一次 UI 重构上。

这条原则适用于进度、心跳与用量等 JSONL 观测事件：解析失败只降低观测精度。最终交付物是 ORGY 主动要求的协议输入；若某工具必须从事件中提取最终消息，该适配器也是交付链的一部分，解析失败须明确记为协议异常并降级到文件交付，不能声称对判定完全无影响。任何一种文本都不能代替 L3 验收。

### 2.4 核心状态不变量

以下十条不变量是引擎的地基。每条都给出客观检测方式，因为无法检测的约定在实现中一定会退化。

| ID | 不变量 | 检测与处置 |
| --- | --- | --- |
| **INV-1** | **单写者**：已接受的 `spec/` 与 `runtime/` 只有持锁 Supervisor 能写；人类编辑 `drafts/` 提案 | 按规范化仓库身份/common Git dir 持有 OS 排他锁；PID 等仅作诊断。所有入口共享同一锁，锁句柄不传给子进程 |
| **INV-2** | **写权限显式授予**：Worker 仅可写声明的源码路径及专属临时、会话、构建与 outbox 目录；交付只经授权通道 | OS 沙箱限制路径；Supervisor 对比 Git 差异与未跟踪文件，越界记为 `SCOPE_VIOLATION`。Git 检查不代替对仓库外写入的阻断 |
| **INV-3** | **快照冻结**：Worker 侧 `spec/` 在一次 Attempt 内固定为派发快照，绝不回流主干 | 候选规范只能由 Supervisor 物化为目标 `spec_revision`；Worker 代码增量不得包含规范文件 |
| **INV-4** | **可恢复提交**：已接受状态可由持久检查点与后续日志恢复，外部动作通过意图与结果对账 | 检查序号、链锚点、对象摘要与操作 ID；仅丢弃未提交尾部，中段损坏停止派发，禁止用重放掩盖缺失事件 |
| **INV-5** | **读集由 Supervisor 证据确定**：规范读集来自注入清单；源码与构建读集来自受限视图或完整访问审计；缺少证据时保守扩大 | 交付时比对条目有效哈希与依赖边摘要；读集无法证明完整时按整个可读项目快照计算，禁用接口级截断 |
| **INV-6** | **写集与资源互斥**：并发执行的任务不得具有相交写集或冲突资源租约 | 检查 `writes.public ∪ writes.private` 与规范化 `resources`；Supervisor 统一处理共享构建配置，验证进程同样获取资源租约 |
| **INV-7** | **验证者权威**：任务验收由受保护的验证计划与精确产物对应的收据判定，自报仅为声明 | 分开记录协议/对账异常与 `VALIDATION_FAILED`；验证器不能被待验代码降低标准，代码、环境和计划变化使收据失效 |
| **INV-8** | **无孤儿复用**：执行实例有独立进程容器及父实例失联后的回收后端，全部进程确认退出后才释放租约 | Windows 使用不可继承控制句柄与 kill-on-close Job；Linux 使用外部管理器托管 cgroup。清理未确认则隔离目录与资源；仅 cgroup/进程组不构成父死子亡保证 |
| **INV-9** | **不可逆副作用需事前授权**：烧录、推送、删库等动作经受控执行边界放行 | 授权绑定动作、目标、参数、产物摘要与有效期；持久化执行意图及结果。结果未知挂起对账，不能自动重复执行 |
| **INV-10** | **约束只存在于条目中**：具有约束力的陈述必须写成结构化条目，散文不具备约束力 | 提交时对散文做规范性语气检查（“必须”/“禁止”/“shall”），命中则告警（§3.6.8） |

+-----------------------------------+---------------------------------------------+
                                    | 只读展示；drafts/ 批次经 orgy CLI 导入
+-----------------------------------v---------------------------------------------+
|                    ORGY Core（Supervisor，唯一写者）                             |
|  +--------------+  +--------------+  +--------------+  +------------------+     |
|  | 调度与状态机  |  | 传输适配器    |  | 客观验证器    |  | 策略与权限引擎    |     |
|  | 增量重算/预算 |  | exec/JSONL   |  | build/test   |  | env/sandbox/探针  |     |
|  +--------------+  +--------------+  +--------------+  +------------------+     |
+----+-------------------------+--------------------------+----------------------+
     | 检查点 + 事务日志       | 执行容器 / 外部回收后端    | Git CAS 操作
+----v-----------------+  +----v----------------+  +------v--------------------+
| .orgy/spec/   [Git]  |  | Worker 进程树      |  | worktree 池与暂存区        |

| - journal.jsonl      |  | stdin : prompt     |  | /worktrees/staging        |

### 3.1 执行层：结构化主路径，PTY 仅作兜底

**主路径：一次性 headless 子进程**

针对支持非交互模式的 CLI 工具（`codex exec`、`dsh --profile headless` 等），ORGY 作为父进程，通过标准输入注入提示词、消费标准输出的事件流、以退出码作为**传输层**的硬边界。

- **确定性生命周期**：退出码与终止信号是“进程如何结束”的唯一事实来源。它不回答“任务是否完成”，但消除了“根据屏幕停滞猜测状态”带来的不确定性。
- **事件流仅作观测**：事件映射为进度心跳与成本统计，由工具适配层按版本解析（§3.4 的能力探针会记录事件格式指纹）。工具若在事件中报告 token 用量则顺带采集，不支持则标记为未知，不做任何正确性假设。
- **双管道持续排空**：stdout 与 stderr 并发独立读取，避免 stderr 缓冲区满使 CLI 假卡死。日志达到上限后截断存储但继续读取，解析器错误不得停止排空；最终交付使用独立有界缓冲或 outbox，不能被普通日志轮转吞掉。
- **强类型交付**：通过 `--output-schema` 或等效手段约束最终消息符合 JSON Schema（§3.2）。这取代自由文本交接日志，使“完成 / 需要澄清 / 受阻”成为可路由的枚举，而不是需要人（或模型）去解读的一段文字。
- **交付通道优先级**：优先使用工具原生 schema 与最终消息提取能力；缺少该能力时使用授权 outbox 或定界符封装（见下）。架构与审查角色是**代码库只读**，仍有专属临时、会话与 outbox 写权限，输出提案由 Supervisor 校验后落盘。
- **长提示词走标准输入**：Windows 的 `cmd.exe` 限制约 8K 字符，直接创建进程也有长度限制；命令行参数还可能出现在进程列表中。以参数数组直接启动，不经 shell 拼接；注入后允许关闭 stdin，不把它假定为运行中的控制通道。

**无 schema 能力时的交付降级**

- 支持文件输出的工具写入本次专属 `.orgy/outbox/<task>.a<n>.handoff.json`；Supervisor 在进程树退出后有界读取，拒绝符号链接、越界路径及不匹配的 Task/Attempt 标识。
- 否则要求最终回答以 `<<<ORGY_HANDOFF_START:<nonce>>>` 与 `<<<ORGY_HANDOFF_END:<nonce>>>` 包裹 JSON。适配器只从本次最终消息提取；无最终消息边界时，从有界捕获输出中接受唯一完整、带本次随机 nonce 的封装，缺失、多份或截断均视为协议异常。nonce 用于避免误匹配，不是认证凭据。
- stdout 可以包含 banner、日志或 JSONL，不要求整个流是纯 JSON。提取后仍做大小限制、JSON Schema 校验、身份对账与客观验证；失败只允许一次结构修复轮。原生 schema 也不保证内容真实。

**降级路径：PTY 用于诊断与人工处理**

PTY 的触发条件必须收窄，并区分两类性质不同的情况：

| 类别 | 含义 | 处置 |
| --- | --- | --- |
| **工具级异常** | 认证失效、许可确认弹窗、未知 CLI 报错、工具崩溃 | 按预算启用 PTY 诊断；仅进度事件畸形不触发重跑 |
| **任务级失败** | 编译错误、测试失败、模型偏离任务 | 进入重试与升级阶梯，**不启用 PTY** |

区分两者很重要：测试失败是非零退出的常态，若把它当作“异常”而进入诊断路径，系统会在最常见的情况下退化回屏幕解析。

PTY 兜底应产出**诊断包**：最近 N KB 原始输出、探测到的弹窗文本、可复现的命令行、环境差异。出路只有两条：

1. 弹窗文本命中工具配置中**预先声明**的允许项时，可自动应答；
2. 其余情况挂起等待人类处理。

不允许从屏幕内容推导出授权决定——那等于把安全策略交给第三方 UI 的措辞。

仅进度事件解析失败时继续采集原始输出，不自动重跑任务。PTY 重拉起是新的、有预算的执行实例；先终止并采集旧实例，使用同样的权限和副作用边界，不能为了诊断自动重复已经可能执行过的外部动作。

**关于“实时接管”的语义澄清**

Windows 无法为一个已存在的进程补挂 ConPTY；类 Unix 系统也需要 tmux/screen 一类复用层才能做到。因此“接管”在工程上只能是 **同环境重新拉起**（respawn with same environment），而不是附着一个正在运行的进程。

本架构不承诺热接管，只承诺交付“可复现命令 + 诊断包”，由人类在自己的终端中继续。这样做的代价是失去运行中的实时干预能力（列入非目标），收益是不必维持一个常驻的伪终端多路复用层。

### 3.2 三层判据与出口路由

任务结论不能由单一信号判定。三层判据如下（对应 INV-7）：

| 层 | 信号 | 回答的问题 | 权威性 |
| --- | --- | --- | --- |
| **L1 传输层** | 退出码、终止信号、是否因超时被终止 | 进程是正常结束还是异常终止 | 硬事实 |
| **L2 协议层** | 交付物的 `status` 与证据字段 | 模型**声称**自己处于什么状态 | 声明，不可采信 |
| **L3 验证层** | Supervisor 自己执行的构建/测试、自己计算的差异 | 客观结果是否成立 | **唯一权威** |

**完成判定**：L1 正常 ∧ L2 为 `COMPLETED` ∧ 该交付类型的 L3 验收全部通过 ∧ 声明与实物一致。代码类完成还需对应集成单元被接受；只读分析、规范提案与审查按各自验收器处理，不能统一要求存在代码 diff。

| L1（按优先级匹配） | L2 交付物 | 处置 |
| --- | --- | --- |
| 被终止、超时或资源违规 | 任意 | 记录取消/超时/隔离原因，终止并采集现场；不接受成功声明 |
| 正常 | 合法 `COMPLETED` | 按 `deliverable_kind` 对账与验收；越界为 `SCOPE_VIOLATION`，声明与实物不符为 `CLAIM_MISMATCH`，验收失败为 `VALIDATION_FAILED` |
| 正常 | 合法 `BLOCKED` / `NEEDS_CLARIFICATION` | 先核查契约摩擦与账本，再修环境、补输入或批量升级；不记为模型失败 |
| 正常 | 缺失或非法 | 一次只修结构的调用，绑定原产物且禁止改代码；仍失败记 `PROTOCOL_ANOMALY` |
| 非零 | 任意 | 不能直接接受成功；先按适配器、退出事实与环境探针诊断，合法阻塞声明仅作线索。可恢复产物经新的受控完成流程重新验收 |

非零退出的 stderr 特征仅辅助分类，不单独决定授权或任务完成；分类不明则 `TOOL_FAILURE_UNKNOWN`，按预算有限重试或转人工。修复轮、诊断重拉起、被终止及失败调用都计入 Attempt/耗时总预算，故障类别可分开统计。

`deliverable_kind` 由 Task 指定并由 schema 判别：`code_change` 提交代码，`spec_proposal` 提交条目操作，`review` 提交结构化裁决，`analysis` / `verification` 提交报告或验证请求。代码任务的 `change_policy: required | optional | forbidden` 决定空 diff 是否允许；需求已满足时可按 `optional` 验证后完成，Worker 不能自行更改策略。规范提案通过导入验证、审查裁决通过策略校验都不等于代码已经通过集成。

**交付物结构**

交付物是机器可解析的声明，人类可读视图由它渲染生成，不得反向修改；事实以 Supervisor 的核验与日志为准：

```json
{
  "schema_version": 1,
  "task_id": "T-2",
  "attempt": 2,
  "session_id": "…",
  "status": "COMPLETED",
  "deliverable_kind": "code_change",
  "summary": "不超过 400 字符",
  "files_changed": ["src/uart.c"],
  "commands": [{ "argv": ["cargo", "test", "-p", "uart"], "exit_code": 0 }],
  "requested_dependencies": [{ "ecosystem": "cargo", "manifest": "Cargo.toml", "name": "serde", "version": "1", "features": ["derive"] }],
  "assumptions_used": ["A-1", "A-2"],
  "contract_friction": [],
  "irreversible_actions": [],
  "questions": [],
  "leftovers": []
}
```

各字段的设计意图：

- schema 同时检查跨字段一致性：`COMPLETED` 不得包含未解决契约摩擦、阻塞问题或待授权的完成前置动作；这些情况应为 `BLOCKED` / `NEEDS_CLARIFICATION`。阻塞时的字段形式为 `contract_friction: [{entry, why_impossible}]` 与 `questions: [{id, text, options, proposed_default, blocks}]`。
- `commands[].exit_code` 不采信模型自述。`argv` 只是复核请求，Supervisor 按任务允许的验证命令选择执行；禁止直接执行模型提供的任意 shell 文本，也不能用其命令替代项目配置的必跑验证。
- 每条验证命令有强制超时、关闭的 stdin（Unix `/dev/null`、Windows 等效空输入）与独立进程容器。超时、正常退出或失败后均清理全部子孙进程，确认结束后才生成可用于验收的收据、释放资源；清理失败也必须记录失败事实。默认拒绝 watch/服务类命令；确需服务的测试由显式 fixture 管理启动、就绪与回收。
- 验证在可重建的候选工作区内执行，产物写入独立构建目录；外部状态使用清理钩子或可复位夹具。关闭 stdin 与超时不等于幂等，无法复位或涉及不可逆副作用的命令按 INV-9 处理。
- `requested_dependencies` 由 Supervisor 校验生态、目标清单、版本约束、features 与来源，再在集成队列中统一解析并更新锁文件；请求不是已安装或已授权的证明（§3.5）。
- `assumptions_used` 与注入清单交叉校验：声称使用了未注入的条目，说明上下文组装有缺陷或模型在幻觉，两种情况都值得记录。
- 交付物**不包含权威读集**。规范注入、源码访问与构建输入由 Supervisor 记录（INV-5），模型可以申请额外输入，但其自述不能证明依赖完整。
- `contract_friction` 触发契约评估；只有 Supervisor 接受规范变更后才按新旧版本计算级联，模型声明本身不修改依赖图。
- `questions` 必须结构化并一次性列全：一次 headless 调用只应消耗一次反问机会，逐条追问会使流水线停滞。
- 模型天然倾向于“直接动手”而非提问，因此账本中已有默认值的疑问应当自答，只有确实需要人决策时才升级，并批量提出。

### 3.3 状态层：冷热分离与单一写者

`.orgy/` 区分提案、已接受规范、运行时与交付出口（对应 INV-1、INV-3、INV-4）：

```text
.orgy/
├── drafts/<proposal>/             # [.gitignore] 人类可编辑的提案批次，非权威
├── spec/                          # [进 Git] 已接受规范的物化视图；Supervisor 写
│   ├── CONTRACT.md                # 接口与协议契约：散文 + 结构化条目
│   ├── ASSUMPTIONS.md             # 假设账本：散文 + 结构化条目
│   ├── tasks/T-2.yaml              # 任务定义：意图与声明，不含运行状态
│   └── verification.yaml          # 已认可的验收计划与必跑检查
├── runtime/                       # [.gitignore] 高频；机器权威的运行时层
│   ├── journal.jsonl              # 追加写事件日志（事实源）
│   ├── state.json                 # 由日志派生的快照，可随时重建
│   ├── checkpoints/               # 持久恢复基点，不能随派生快照一起删除
│   ├── receipts/                  # 验证收据（§3.6.5）
│   ├── recoveries/T-2.a2.json      # Supervisor 的终止后采集记录
│   ├── logs/T-2.a2.jsonl          # 原始事件流与退出码审计，兼作诊断素材
│   └── supervisor.lock            # OS 锁的诊断元数据；锁按仓库身份统一
└── outbox/                        # [仅存在于 Worker 工作区内，.gitignore]
    └── T-2.a2.handoff.json        # 本次授权的文件交付通道
```

**关键约束及其理由**

- `spec/` 只承载意图与声明，**不含任何运行状态**。任务状态进入 `spec/` 会诱使人类手工编辑状态字段，破坏账本与事实的一致性。
- `runtime/` 不允许手工编辑。`state.json` 可从持久检查点与后续日志重建，不能把它与不可丢弃的恢复检查点混同。需要变更状态时使用 `orgy` 命令行，由 Supervisor 写入日志。
- `tasks/*.yaml` 必须声明目标、验收计划、交付类型及 `inputs`、`writes.public/private`、`resources` 与 `implements`（无资源时显式为空，见 §3.6.2）。缺少读集证据时按 §3.6.4 保守扩大，而不是假定没有依赖。
- outbox 文件名必须包含尝试序号，否则重试会覆盖上一次的交付物并产生读取竞态。

**事件日志与崩溃恢复（INV-4）**

启动先按规范化仓库身份获取 OS 排他文件锁或命名互斥量，生命周期内持有；所有 worktree 入口定位到同一运行态和锁。PID、主机名与启动时间仅供诊断，不承担互斥。MVP 限于单机可靠本地文件系统；跨主机共享运行态未实现 fencing 前禁止多实例调度。

事件结构：`{seq, ts, epoch, operation_id, type, actor, task_id, payload, prev}`。`prev` 连接上一条记录，配合检查点链锚点检测缺失与损坏；能同时改写日志及锚点的主体仍能伪造它，不把哈希链当作独立防篡改证明。

已接受状态变更先追加完整事务记录并 fsync，随后以临时文件及原子替换更新 `state.json` 等物化视图；未持久化事务不得向调度器发布。`state.json` 记录已折叠序号与链哈希，恢复时先验证，再从检查点或后续日志重放。

- 只允许自动丢弃末尾未提交的不完整记录；中段损坏、序号缺失、完整记录校验失败均隔离日志并停止派发，不能通过“重放”修复丢失事实。
- 检查点包含完整折叠状态、最后序号/链哈希、schema 版本和引用对象清单。新检查点及所引用对象持久化并校验后再发布恢复索引；至少保留上一有效代际和从该代际重放所需日志，才可回收更老段。恢复索引与检查点损坏不能导致盲目从空状态启动。
- `state.json` 可丢弃；检查点、恢复索引、未完成操作意图及其引用对象按保留策略保护。GC 不得删除恢复链、在途候选、批准动作或活动 Session 仍引用的对象。
- 各平台后端需验证 flush、原子替换及断电恢复能力；Windows 不能以重命名成功代替目录持久化证明。声明的保证以故障注入结果为准，持久化失败停止对外确认。

**外部动作不能靠日志重放获得原子性**

启动进程、发布 Git ref、物化多文件规范或操作设备，均采用 `operation_id + intent(expected_state, target_state) → execute → outcome`。意图先持久化，重启后查询事实并对账，不机械重执行命令：

- Git 晋升意图保存接受 ref 名、`expected_commit`、`target_commit`、`spec_revision`、`plan_digest` 与 `receipt_refs`，使用预期旧值的原子 CAS。当前 ref 已等于目标时补记结果；仍等于预期旧值且输入有效时可继续；其余状态进入冲突恢复。启动先对账未决晋升，再接受新规范或新晋升，避免恢复阶段交错更新。
- 进程启动绑定持久执行实例 ID，由执行后端实现同 ID 不重复启动；恢复先查旧容器并完成回收，再允许新 Attempt。
- 规范以不可变 `spec_revision` 发布，完整内容在提交事务前保存并校验；多文件 `spec/` 仅是可重新物化的视图，调度从不读取物化中的半批文件。
- 不可逆动作的结果若不可查询且未落盘，则为 `UNKNOWN`，停下来核对；没有外部幂等协议时不承诺 exactly-once。

执行生命周期（排队、运行、终止中、等待输入、待集成、已接受、失败、取消）由这些事件折叠，独立于收据派生的 `FRESH/STALE/DIRTY`。每个 Task 只能有一个活动 Attempt、每个集成单元只能有一个有效晋升操作；迟到退出事件按执行 ID 归档，不能改变新 Attempt。

**读集乐观并发：以条目哈希取代全局版本号（INV-5）**

一种自然但错误的做法是：维护一个全局版本号，任何规范变更都使其递增，并要求所有在途任务的交付物版本号与之匹配。这会导致“人类修改了一条无关假设，却使全部在途任务被拒收重派”，容错退化为反复折腾。

正确的做法是内容寻址加读集比对：

- 规范变更后，更新**条目级**有效哈希（§3.6.3）；全局 `epoch` 仍然递增，但只用于审计与看板展示。
- 派发任务时记录注入清单（含任务自身定义与验收计划）。条目有效哈希变化则旧结果不能验收；仅有无关条目变化正常接收。纯源码/环境漂移先使旧验证收据失效，保留冻结基线上的工作，进入最新基线重验流程（§3.6.6），不一律杀进程。
- **规范目标/验收计划失效或权限收窄时按依赖证据抢占**；超时、取消与权限违规另行处理。不要求一次性 CLI 在收到信号后生成 `PREEMPTED` 交付物。Supervisor 记录终止意图，将整棵进程树停止；可给予工具已支持的 OS 退出清理短暂时限，到期强杀，正确性不依赖清理回调。
- **终止后采集（Post-mortem Harvesting）**：确认进程树退出后，Supervisor 采集基线提交、`git status --porcelain`、相对基线的完整差异（含已暂存变化）、声明范围内未跟踪文件与日志尾部，保存不可变 Attempt 快照及恢复记录（§3.5）。日志解析失败不阻止恢复；其中的模型陈述仅作非权威线索，不能证明完成或副作用已执行。
- 抢占原因由 Supervisor 写为 `PREEMPTED` 事件，L1 仍计为 `KILLED`。下次 Attempt 接收新输入与恢复摘要；无完整交付物也能恢复。进程或快照保全未成功时隔离现场，禁止 reset 或复用。

**架构角色的写入路径**

架构角色同样不直接写主工作区。它输出结构化变更提案：对条目执行 `add` / `set` / `retire` 的操作，并附带基线 `spec_revision` 与目标文件的 `base_hash`。Supervisor 在提交临界区校验后发布新版本：

1. schema 校验；
2. `base_hash` 比对（乐观并发，防止覆盖人类的同时编辑）；
3. 全图语义与引用校验（§3.6.10）；未被任务引用的接口给出规划告警，不阻止分阶段建模。

**人类编辑的仲裁规则**

- 人类编辑 `.orgy/drafts/<proposal>/`，由导入命令或 UI 提交动作一次性封存该批文件、预期文件摘要与基线版本；复制过程中若文件变化则重试封存，不能接受混合批次。文件监视只负责预览/检查，不把去抖当事务边界。
- Supervisor 对封存提案验证后在提交临界区再次检查基线，日志确认接受后更新 `spec/`。不同提案的冲突保留给人处理；不会覆盖仍在编辑的草稿。
- 人类提案在待处理队列中优先，但不得撤销已提交事实。模型旧提案基线不匹配时重新生成或明确解决冲突，不悄悄覆盖。
- 直接编辑受管 `spec/` 属于越权更改：保全为待导入草稿并告警，调度继续使用最近已接受不可变版本，不把原地文件当成新事实。

规范版本与代码接受版本分开记录。规范变更不自动使旧代码“通过新规范”；只有携带目标 `spec_revision` 的集成单元验证通过，才更新已接受的代码/规范组合。Git 中保存不可变规范对象及受管 refs，导入、代码晋升和恢复均引用明确版本。

### 3.4 隔离与权限治理

不同 CLI 对配置目录、缓存路径、写入权限与网络访问的沙箱假设差异很大。若不统一接管环境，跨工具调度会频繁失败。例如在受限沙箱中启动 `dsh --profile headless` 时，可能因为无法创建 `~/.dsh/profiles/<name>` 而直接以 `EPERM` 退出——这类失败与任务本身无关，却会被误判为“工具坏了”。

**环境隔离的推荐次序**

1. **优先使用经探针验证的工具原生开关，而不是伪造 HOME**。配置覆盖、临时会话与目录授权等能力均按工具及版本登记，不假定某组参数在所有版本可用；原生参数控制配置加载，OS 沙箱控制实际权限。
2. **凭证按用途最小化传递**。不把凭证复制到临时项目目录；优先使用用户授权的代理/句柄，必要时向模型 CLI 注入最小环境或只读凭证挂载。环境变量仍可被 CLI 子进程继承，不能视为凭证隔离。验证、依赖解析与 Git helper 使用独立环境允许列表，不继承模型 Key、SSH agent 或推送凭证；日志和诊断输出脱敏。
3. **按生命周期拆分隔离目录**。Task 的 CWD、会话状态与本地构建目录保持稳定；Attempt 的临时目录与 outbox 单独分配。将实际生效的 `TMPDIR` / `TEMP` / `TMP` 和工具状态目录指向授权位置，避免工具在真实用户目录写状态。退出后先收集交付与诊断，再销毁临时区；会话按 Task 租约保留。
4. **Windows 平台差异**：多数工具读取 `%USERPROFILE%`、`%APPDATA%`、`%LOCALAPPDATA%`，不读取 `HOME` 或 `XDG_*`。工具配置必须逐个注明“哪些变量真正影响它”，否则隔离在该平台上不具备实际效果。

**声明式能力矩阵**

| 角色 | 沙箱级别 | 可写路径 | 任务工具网络 | 交付方式 |
| --- | --- | --- | --- | --- |
| 架构统筹 | 代码库只读 | 专属临时区、会话目录、授权 outbox | 默认禁止 | 最终消息 / outbox / 定界符 |
| 核心构建 | 声明源码路径可写 | 写集 + 专属临时、会话、构建、outbox 目录 | 经代理授权包仓库 | 同上 |
| 测试与工具 | 声明源码路径可写 | 同核心构建 | 默认禁止（验证需可复现） | 同上 |
| 对抗性审查 | 代码库只读 | 专属临时区、会话目录、授权 outbox | 默认禁止 | 同上 |

**两个容易被忽略的维度**

- **缓存策略**。每个 Task 与每个集成候选使用独立 `target/`、`build/`、包管理器可写元数据和锁目录，禁止并发共用可写 `CARGO_TARGET_DIR`。包下载内容由受信下载服务校验完整性后原子发布为只读缓存；包管理器需要可写缓存时使用私有覆盖层，不把整个 `~/.cargo` / `~/.npm` 当作天然只读或只追加目录。编译缓存可通过 `sccache` / `ccache` 的受控服务共享，键包含工具链、目标、参数及输入摘要，并隔离信任域；CoW 基线克隆只作为可选优化。
- **网络策略**。Worker 与验证沙箱默认无直接外网路由；仅开放到受控出口代理的路径，并阻断其他直连。注入 `HTTP_PROXY` / `HTTPS_PROXY` 等只是客户端配置，不能形成安全边界。不支持代理的工具须有经探针验证的转接方案，否则拒绝该联网能力。

**受控出口代理**

代理是 Supervisor 管理的独立组件，执行域名、端口、协议策略与审计。Linux 可通过网络命名空间与防火墙实现强制出口；Windows/macOS 使用对应的网络隔离与防火墙能力，Job Object 本身不限制网络。完全断网的命名空间无法访问宿主代理，因此必须显式配置到代理的唯一受限通道；不得开放整个宿主 loopback。

域名匹配由代理解析 HTTP 目标或 CONNECT/SOCKS5 的域名请求，DNS 在受控侧解析；拒绝未授权 IP 字面量、私网/元数据地址及重绑定，仓库 CDN、下载域名与重定向目标均需单独授权。普通 HTTPS CONNECT 只约束隧道目的地，不能审查加密内容，也不自动阻止向获准服务上传数据；若要求内容级限制，需要单独的仓库网关或经配置的 TLS 检查，不在基础承诺内。

模型 CLI 自身仍需访问模型服务和认证端点，应与任务工具的包仓库权限分开登记。若 CLI 与其子工具无法在身份或网络通道上分离，二者共享该进程树的最小出口权限，必须如实记录这一限制；“审查角色禁止联网”仅指任务工具业务访问，不能切断其推理连接。

**其余硬性约束**

- **工作目录参数不是隔离边界**。`-C` 只能防止“走错目录”，无法阻止主动读写其他路径。用受限令牌、AppContainer、挂载视图或容器等限制文件访问；Job Object 负责进程生命周期，不能单独提供文件隔离。源码读边界须覆盖符号链接、共享 Git 对象库、工具缓存与其他 worktree，Sparse Checkout 只是材料裁剪手段，不能单独阻止 `git show` 或路径逃逸。
- **嵌套沙箱**。ORGY 自身很可能运行在别人的沙箱或受限令牌内。策略引擎需要“父沙箱已存在”模式：探针先测出实际可写范围与可创建目录，再在此基础上**收窄**，而不是假设自己拥有完整权限。
- **启动前探针产出能力清单**（而非通过/失败）。清单包含 headless、最终消息提取与 schema 实效、事件格式、续接与 CWD 要求、配置/会话/临时目录、认证、退出码语义，以及实际文件/网络阻断和子孙进程回收能力。用极小任务实测，不以参数被接受代替隔离验证。结果按（工具版本、配置哈希、策略哈希）缓存；仅源码视图/读取审计不足可回退保守读集，必要的写隔离、网络阻断或回收能力缺失必须拒绝相应任务，不能用扩大读集补偿。

若 CLI 不能隔离其子工具的凭证与推理出口，则整个 Worker 进程树属于同一凭证信任域，明确登记这一能力限制。独立验证器仍使用无模型凭证的沙箱，不能复用 Worker 的环境。

**控制面不执行仓库代码**

Supervisor 只做编排、数据校验与受控 Git 元数据操作。包管理器、构建器、测试与可能执行项目脚本的转换器均在 helper 沙箱中运行，其可写范围不包含权威规范、日志、共享 refs 或其他工作区。固定 `argv` 不能阻止 `build.rs`、pytest 插件或安装脚本执行任意仓库代码。

Git 管理操作使用受管配置与环境，禁用 hooks、外部 diff/textconv、未批准的 clean/smudge 过滤器；不加载不受信任的仓库扩展配置。需要过滤转换的项目先在受限 helper 中生成显式产物，再对账并保存快照，不能让 Supervisor 在提交时隐式执行它们。

**父实例消失后的执行回收**

Windows 优先用 `PROC_THREAD_ATTRIBUTE_JOB_LIST` 在创建时原子归属禁止 breakaway 且启用 `KILL_ON_JOB_CLOSE` 的 Job，控制句柄不被子进程继承。旧系统若采用挂起创建再入组，必须由独立启动所有者管理并回收“已创建未入组”窗口，不能把挂起状态视作无泄漏。Linux 的 cgroup 配合外部服务管理器或独立 watchdog，按 owner 失联协议停止整组进程；不能仅依赖已经死亡的 Supervisor 执行清理，也不允许 Worker 写 cgroup 管理接口。后端须经过各启动边界及父进程强杀测试。

启动恢复取得仓库锁后，先枚举持久执行 ID 对应容器、确认回收并采集现场，再重新发放资源或复用目录。缺少可靠 owner-death 后端的平台只提供“失联后隔离，确认清理后恢复”，不得宣称立即父死子亡，也不得自动继续占用该现场的任务。

**受保护的验收计划与不可变被测对象**

`spec/verification.yaml` 定义必跑检查 ID、受信 runner/回归测试版本、目标、超时、资源、预期用例和跳过策略。实现任务不能修改该计划；候选新增测试是补充，删除/放宽基线检查、golden 数据或测试发现规则需单独的规范变更与认可，不能靠候选自己的零退出码自动生效。不能枚举用例的检查须定义替代成功判据；零用例或非允许跳过按失败处理。

验收从精确候选快照启动，源码只读、构建和临时输出外置；确需生成受跟踪源码时先创建新候选，再冻结并验证。验收 runner/最低验收集位于受保护输入，项目程序仍在受限子环境执行。收据记录预期与实际检查集合、每项结果和输入摘要，结束后核对候选输入未变。候选可修改的测试不能独自证明任务完成。

接受验证从空的候选本地构建目录开始；仅可复用具有完整输入键、受信发布者和完整性校验的内容缓存，不把 Task 遗留的 `target/` 直接带入。MVP 可禁用编译缓存；普通增量自检可继续使用 Task 缓存，但它不能代替接受验证。

### 3.5 工作区隔离与两阶段验证

**Task 工作区与 Attempt 快照**

每个 Task 使用固定路径 `/worktrees/<task>`，租约覆盖多次 Attempt，同一 Task 不得并发执行两个 Attempt。Supervisor 管理 Git 元数据与提交；采用 detached HEAD 或专属 Task 分支，避免将同一分支同时检出到多个 worktree。Worker 不得改动共享 refs、hooks 或其他任务元数据。

文中“主干/main”指受管接受 ref，默认使用 `refs/orgy/accepted`，从用户选定提交初始化；不直接移动用户正在检出的分支。向用户分支集成或向远端发布是明确的后续操作。这样接受候选不会使人类工作区的 HEAD、索引和文件脱节。

Attempt 结束后先确认进程树静止，再由 Supervisor 将声明范围内的代码变化（含暂存与未暂存修改、删除、合规未跟踪文件）保存为不可变快照提交，固定到 `refs/orgy/attempts/<task>/<n>`。记录基线、快照、会话标识及恢复摘要；不盲目 `git add -A` 收入缓存、凭证或 outbox。越界文件另存隔离证据，不进入候选代码。该 ref 只表示恢复点，不表示验证通过。

`restart` 保留现场并按 §2.1 续接；`reset` 在快照成功后才由 Supervisor 将受管代码还原到选定基线，显式处理未跟踪文件，保留授权缓存与会话策略要求的内容。`git reset --hard` 本身不会清理未跟踪文件，不能代表完整恢复。旧 diff 作为上下文提供，不自动重新应用被放弃的变更。切换基线后更新规范快照和输入清单；一次 Attempt 内快照保持冻结。回收只针对无活进程、无有效租约且恢复资料已保全的目录。

**写集与物理资源**

调度器检查 `writes.public ∪ writes.private` 的路径交集；worktree 只是实现隔离的手段，不保证语义兼容。默认串行，只在契约接缝处并行。路径规范化须考虑大小写、符号链接与通配符，不能确定不相交时保守串行。

`resources` 声明独占资源，如 `hw:board-1`、`hw:stlink-1`、`port:8080`。资源注册表将 `/dev/ttyUSB0`、其稳定设备名与同板 JTAG 映射到同一板卡资源，防止别名绕锁。MVP 按 Task 执行阶段保守持有整组租约；验证命令也原子获取全部所需资源。仅在进程树清理、设备复位或隔离完成后释放；租约过期不证明硬件空闲。多 Supervisor/外部用户共享设备时需要公共租约服务或专用设备池，进程内锁只能约束本实例。资源锁不代替烧录等不可逆动作授权。

写集租约覆盖活跃修改阶段，硬件租约覆盖实际使用阶段；结束后释放，排队/等输入时不空占设备。局部验证接管已有资源或在释放后重新获取，不能一边由 Task 持有、一边要求验证器重新获取同一把非重入锁。跨主机资源由能拒绝旧 fencing token 的设备代理管理；无法 fencing 的设备须专用占用或人工确认隔离。

**共享构建配置单写者**

默认禁止 Worker 修改构建清单及锁文件，由 `requested_dependencies` 提出需求；其他构建配置变更提交结构化提案。Supervisor 在合并队列上基于最新候选状态统一修改，校验版本约束冲突、来源与脚本执行策略，并记录解析器版本、锁文件和生成差异。`cargo add` / `npm install` 等会依赖仓库状态、联网或运行脚本，不视为天然确定性工具；后续验证使用已锁定结果和受控下载输入。

局部检查需要新依赖时，Supervisor 可在任务私有环境生成有记录的依赖覆盖；它不成为 Worker 的提交。集成时重新解析冲突并执行完整验证。不能结构化表达的清单变更交给专门集成任务，在最新已接受基线上串行执行；不以运行期路径锁承诺消除分支冲突，也不在活跃 Worker 下自动 rebase。

**两阶段验证与串行合并队列**

1. **局部检查与对账**：Worker 自检后，Supervisor 对比 `files_changed`、实际差异与写集，复核预定的局部命令；依赖覆盖的生成差异单独对账。对账覆盖删除、模式变化及未跟踪/被忽略的受管文件，不能让 `.gitignore` 隐藏产物。对账及适用局部检查通过可发布冻结候选，不代表完整验收或合入。
2. **队列排序**：以集成单元为粒度，先满足依赖拓扑，再按就绪完成顺序排队。以已接受代码 `S0` 为基线，为单元 `U1` 构造 `S1 = S0 + U1 + Supervisor 配置/规范变更`，在隔离 staging 上按目标规范运行完整验收计划。若旧 `S0` 尚未满足新规范，记录其旧通过版本和已知失败，不能将迁移所需失败误判为环境异常。
3. **按已验证提交晋升**：完整验收及所需审查通过后，在同一提交临界区重查目标规范/计划、权限与资源条件，并对接受 ref 执行预期旧值为 `S0` 的 CAS；仅晋升精确 `S1`。基线或约束变化则重建/重验；任何审查后修改使旧收据失效。晋升意图与结果按 §3.3 对账恢复。
4. **投机执行为可选优化**：允许在独立 `/worktrees/staging/<candidate>` 上预验 `S2 = S1 + U2`，但必须等 `S1` 接受后按序晋升。前驱失败、撤销或重写时，后续候选及收据作废，从最新接受基线重建。MVP 只做串行队列。
5. **失败定位与路由**：失败先隔离当前集成单元，发送差异与日志给其责任任务；此前已接受单元不被连坐打回。队列定位的是失败增量，不证明某任务单独有错。复跑同规范/同环境的已知通过基线、最小组合复现或有限二分可辅助归因；新规范下从未通过的基线不能充当回归证据。诊断重跑有预算，不能无限重跑直到通过。

所有候选均执行完整验证，不允许 `public_digest` 截断该阶段。验证命令的超时、无交互、进程回收与副作用规则见 §3.2。

**跨任务接口迁移的原子集成**

单任务无法独立通过新规范时，优先改为一个垂直切片；确需多个 Worker 时，在任务定义中声明共同的 `integration_group`，同时固定组成员、目标规范、内部依赖与预算。例如驱动接口变更与解析器迁移组成一组，避免“驱动等旧解析器测试通过，解析器又等驱动先接受”的环形等待。

组内按无环依赖消费上游不可变候选产物（绑定候选 ID 与摘要），不要求上游已晋升；上游重写则相关组内候选失效。组外只消费已接受结果。组内仍遵守写集/资源互斥，完整验收针对合成后的单个候选执行，整组 CAS 晋升；某成员失败只重做受影响成员，保留其余快照。组大小/耗时有上限，不自动把整条闭包扩成无限批次；规范切换所需的受影响消费者必须纳入组或采用兼容迁移，不能靠跳过检查推进。

验收计划预先区分 `member-local` 与 `group-only` 检查：依赖尚未迁移消费者的全项目编译属于后者，组员完成对账及可独立检查后即可发布组内候选，将组级检查标为 pending。若不存在可独立的语义检查，至少完成协议/范围对账，但不得声称已验证功能。整组所有必跑检查通过才接受，不能运行失败后临时把检查改为延期。

**防止规范层回流与副作用**

Worker 的 `.orgy/spec` 为只读快照；Supervisor 只应用经对账的代码增量，不合并旧规范。候选规范由 Supervisor 从目标 `spec_revision` 物化并核对摘要；与目标不符记 `SPEC_LEAK`，目标已变则重新入队。正常规范迁移允许受控规范差异，不再要求相对旧主干永远为空。不依赖本地 Git 合并驱动配置。

硬件、推送与外部写入通过受控动作执行器（broker）完成，Worker 默认没有可绕过它的原始设备/远端写权限。请求携带 `action_id`、稳定目标身份、参数与产物摘要；授权限定范围、次数与有效期，执行器验证当前资源 fencing 后先持久化意图，再执行并记录结果。外部系统支持幂等键时复用该 ID，结果未知则挂起对账。

串口/JTAG 的原始句柄通常无法区分“查询”和“烧录”；无法细分的工具按整条命令最高副作用能力在执行前授权，并由执行器持有设备。`irreversible_actions` 只是申请，漏报也不能获得句柄。已经开始的不可逆操作不会因普通 Worker 抢占而自动重启；由执行器完成安全停止或进入未知态隔离，资源未确认前不释放。

### 3.6 语义化规范层与增量重算

#### 3.6.1 动机

如果规范只以散文存在，就无法回答两个必须回答的问题：

1. 修改了某个接口，哪些任务受影响？
2. 人类修改了某条假设，哪些产出需要重算？

回答不了，级联重置就退化为全量重启，增量收益为零。因此规范层必须同时满足两个看似冲突的要求：**人类可读、可自由组织**，以及**机器可解析、可精确求差**。

解决方案是“文学化结构化规范”（literate structured spec）：散文照常书写，所有具备约束力的内容封装在带语言标签的围栏代码块中，并赋予全局唯一、不可复用的稳定 ID。

#### 3.6.2 条目格式

假设条目（`spec/ASSUMPTIONS.md`）：

````markdown
### 硬件通信层

雷达模块经开发板 UART2 接入，初期未启用 DMA，采用轮询读取：

```yaml assumption
id: A-1
topic: 雷达串口波特率
value_type: integer
value: 115200
status: active
rationale: 该波特率与雷达模组出厂固件一致
```
````

契约条目（`spec/CONTRACT.md`）：

```yaml contract
id: IF-3
kind: interface
depends_on: [A-1, A-2]
sig: "int uart_read(uint8_t *buf, size_t len)"
invariants:
  - 成功时返回读取字节数，硬件错误返回负值
  - 非阻塞，必须在 1ms 内返回
```

任务条目（`spec/tasks/T-4.yaml`）：

```yaml task
id: T-4
title: 实现雷达字节流解析器
objective: 将字节流解析成完整雷达帧，拒绝长度错误和校验失败的帧
role: core_builder
deliverable_kind: code_change
change_policy: optional
acceptance: [parser.valid_frame, parser.invalid_frame, regression.required]
verification_plan: parser-v1
integration_group: null
inputs:
  contracts: [IF-3, IF-4]
  assumptions: [A-2]
  tasks:
    - id: T-2
      mode: public
      paths: [include/uart.h]
  source_paths: [src/parser.c, include/parser.h]
writes:
  public: [include/parser.h]
  private: [src/parser.c]
resources: []
implements:
  - contract: IF-4
    target: host
    implementation: parser.default
```

上述条目是格式片段，省略的 `A-2`、`IF-4`、`T-2` 及验收计划须在实际规范中存在。`objective` 与 `acceptance` 是验收约束；`title` 仅供界面展示。验证计划由受保护配置定义，包含必跑命令及成功判据，不能只凭“实现了某接口”推导完成。

`inputs.tasks[].mode` 可为 `public` 或 `full`，缺省按 `full` 处理；`public` 申请仅依赖上游公开产物，须满足 §3.6.4 的读取隔离条件才生效。`paths` 申请公开视图内的文件，不授权读取私有实现；`source_paths` 申请自身或其他显式源码输入。`writes.public/private` 表示依赖可见性，不表示不同写权限，两者都计入互斥检查。公开文件中的 inline、宏、模板等实现同样按字节计入公开摘要，不自动视作纯签名。

硬件任务可声明 `resources: [hw:board-1, hw:stlink-1, port:8080]`；资源别名与整板独占关系由注册表解析（§3.5）。

**一个代码块只放一条条目**，便于 ID 定位、差异与提案合并，但不保证 Git 永不冲突。条目增多后按主题拆分文件（如 `ASSUMPTIONS.hw-uart.md`）；低频规范统一导入后，优先做按 ID 的提案对账，不引入复杂的自定义 Markdown 合并驱动。

**ID 与命名空间**：`A-*` 表示假设，`IF-*` 表示接口，`T-*` 表示任务，`INV-*` 表示本文档中的不变量。条目 ID **不可复用**：删除条目时保留块并标记 `status: retired`，禁止删块后把同一 ID 分配给新条目。否则历史交付物中的读集哈希可能“恰好”匹配到一个无关的新条目，产生假阴性。

#### 3.6.3 语义投影与有效哈希

**第一步：语义投影。** 对条目文本直接取哈希是错误做法，因为块内的排版调整、说明性字段修改都会触发级联。正确的做法是每种条目声明一份**语义投影白名单**，只对具备约束力的字段取哈希：

```yaml
# 工具配置中的投影定义
assumption:
  semantic: [id, topic, value_type, value]
  ignore:   [rationale, note, owner, last_verified, status]
  # status 仅 active/confirmed 互转时忽略；进入 retired 按删除处理（§3.6.6）
contract:
  semantic: [id, kind, sig, invariants]
  ordered:  { invariants: false }
task:
  semantic: [id, objective, role, deliverable_kind, change_policy, acceptance, verification_plan, integration_group, writes, resources, implements]
  ignore:   [title, notes]
```

`depends_on`、`inputs` 的依赖描述单独规范化并参与有效哈希，包含目标 ID、边类型、`mode` 与路径选择，不能只哈希目标内容而遗漏边的含义。规范依赖与代码产物依赖分开求值，后者另进入任务输入摘要。

`verification_plan` 解析为受保护验收计划的版本化内容哈希；组成员 ID、内部边与目标规范的声明进入组摘要，但不把成员的有效哈希再滚回该声明，避免“任务依赖组、组又依赖任务”的哈希环。集成候选另外绑定全部成员定义与产物摘要。任务自身定义和这些控制依赖强制进入注入清单，不能由 Worker 的 `inputs` 申请省略。调度用预算/模型配置同样版本化记录，但不把纯成本参数当作代码行为改变。

三条要点：

- **`status` 的语义需要拆分**。`active ↔ confirmed` 只是元信息，人类“确认某条假设”不应触发任何重算，因此不进入语义投影。但 `→ retired` 是语义终止事件，必须按删除处理（§3.6.6），否则会出现“假设已作废但没有任何产物被重算”的静默过期。
- **集合与有序序列必须显式区分**。`invariants` 是集合，排序后再哈希；但硬件场景中 UART 寄存器初始化序列的**顺序本身是语义**，此类字段需要 `ordered: true`。不区分会得到“顺序改了但哈希没变”的错误结果，比多算一次更糟。
- **按 schema 归一化**。默认保留标量类型，整数 `115200` 与字符串 `"115200"` 不等价；`value_type: integer` 下拒绝字符串，只有显式转换规则才可转换。注释和合法空白可忽略。版本号、标识符、浮点值与有序字节不得用通用字符串/数字转换抹平；拒绝重复 YAML 键及不受支持的隐式类型。

**第二步：有效哈希（Merkle 滚动）。** 仅靠内容哈希无法表达“接口内容没变、但它依赖的假设变了”这种间接影响。与其为此增设“间接受影响”之类的中间状态，不如把依赖关系滚进哈希本身：

```text
content(e)   = H( schema_version, projection_version, normalization_version,
                  kind, id, projection(e) )
effective(e) = H( id, content(e), normalized_dependency_descriptors(e),
                  sort[ (id(d), effective(d)) for d in spec_deps(e) ] )
```

其中 `H` 为哈希函数（如 SHA-256），编码使用无歧义的规范序列化。`projection(e)` 是条目的语义投影，`spec_deps(e)` 包含显式规范依赖与上述验收/组控制依赖。依赖集合先排序，书写顺序不影响结果；schema、投影或规范化规则变化使对应旧摘要失效。

这样做的直接收益是**失效判定只剩一条规则**：

> 规范读集内条目的有效哈希变化即使该输入失效；全部规范哈希未变仅说明规范输入未失效。

规范变化沿规范依赖链滚动；源码、工具链与运行环境是否失效仍需独立检查（§3.6.5）。

调度图区分规范边、控制依赖与产物边。`inputs.tasks` 是**产物边**：组外等待上游接受，组内可按 §3.5 消费冻结候选，再按读取证据选取 `public_digest` 或 `artifact_digest`。不把上游任务的规范有效哈希无条件滚入下游；下游直接读取上游契约时，该规范边独立失效，不能被产物摘要相同截断。

#### 3.6.4 规范注入与源码读集

整套增量计算都依赖“任务的依赖声明是完整的”这一前提。但实际中模型会系统性地**少写**依赖——它可能从别处抄了一个常量，并不认为自己“依赖”某条假设。少写的后果不是多算，而是**该重算的没有重算，代码库中留下静默过期的产物**，且没有任何信号。

Supervisor 精确知道注入了哪些规范条目及版本，但这仅覆盖**规范读集**。Worker 通过 `cat`、`grep`、编译器、Git 历史或旧会话得到的源码信息，不会自动出现在注入清单中。

因此：

- 派发时记录 `injection_manifest`（含任务自身、验收计划、组定义及其他条目的 ID 与有效哈希），作为规范读集；
- `inputs` 从“声明”降级为“申请”——任务表达它希望获得哪些条目，Supervisor 记录实际授予的集合；
- 同时记录 `source_manifest`：受限视图的全部可读项目输入及摘要，或覆盖完整进程树的源码/构建读取审计结果；构建工具、生成输入、依赖锁文件等进入相应输入或环境摘要；
- 交付时检查上述证据与当前输入（INV-5），读取能力变化也使旧收据失效。

规范读取也受同一边界约束：执行 Worker 默认获得按语义字段生成的条目视图，不把被忽略的 `notes/title/rationale` 或散文当作指令注入。若允许直接读取原始规范文件，则其全部可读条目和原始字节摘要都纳入读集；此模式下修改散文也可能使生成上下文失效，不能同时承诺忽略这些字节。架构角色可读原稿以形成提案，正式约束仍须导入。角色提示模板、项目指令与工具配置纳入派发策略摘要。

源码依赖采用以下分级策略：

1. **默认保守模式**：全量项目源码可读时，按整个可读项目快照（排除明确无关的缓存/日志）计算源码输入，不声称仅依赖接口。实现文件改动也会使收据失效；这是牺牲截断收益换取依赖完整性。
2. **受限接口视图**：只暴露声明的自身源码、上游公开文件/接口包及受控构建输入，隐藏其他模块实现、历史对象与外部别名路径。全量集成由独立验证沙箱执行；若局部编译必须读取上游实现，该验证动作按 `full` 依赖处理，不能共用仅接口的收据。
3. **完整访问审计**：可用平台文件访问审计采集所有子孙进程实际读取、目录枚举及不存在路径查询，覆盖生成文件、链接与 mmap 等读取方式。`strace` / `fs_usage` 只是候选工具，丢事件、缺少子进程覆盖或无法追踪某类访问时，不足以证明完整，回退保守模式。未申请但仍获授权的读取须扩大依赖；超出授权视图的读取属于隔离违规，终止并重新建立边界，不能事后补声明来洗掉违规。

同一 Session 已读过的信息也是输入：续接时继承历史读集并集，或切换新会话后重新建立边界。缩小视图却续接含私有实现的旧会话，不能恢复接口级截断资格。仅在视图或审计证明不依赖私有实现、所有其他输入未变时，`mode: public` 才有效。

输入来源与验收证据分开记录：`generation_manifest` 永久保存本次模型实际看过的基线、规范与会话输入；`validation_manifest` 描述当前候选重验时的真实输入。源码证据再区分外部输入、自有文件修改前像与生成中间产物；自有前像仅用于生成来源和三方应用，最终文件由 `code_digest` 覆盖，不能一合入就因自身修改被判失效。

同一路径的外部并发修改不属于“自身修改”豁免：Supervisor 依据 base/ours/theirs 对账，冲突须重新修复。当前验收通过不能改写生成清单，伪称模型已经看过新输入。实际读过上游私有实现时，将相应产物依赖升级为 `full` 并去重；保守全库读仍保留全量外部证据，不能靠较窄的 `mode: public` 抹掉它。

#### 3.6.5 验证收据与派生状态

新鲜度由验证收据派生，不作为可独立编辑的事实；可缓存派生状态，但须携带日志序号并能重算。执行生命周期仍按 §3.3 存事件，不能用 `FRESH` 表达“当前是否有进程运行”。

```yaml
receipt:
  task: T-4
  execution_id: T-4.a2.verify1
  scope: local             # local / integration；两种收据不能相互替代
  spec_revision: sha256:…
  task_definition_digest: sha256:…
  generation_manifest_ref: runtime/manifests/T-4.a2.generation.json
  inputs_digest: sha256:…   # validation_manifest：当前规范、外部源码及产物边
  code_digest:   sha256:…   # local 为任务产物；integration 为完整候选树
  env_digest:    sha256:…   # 工具链、命令、策略、锁文件及资源/fixture 配置
  verification_plan_digest: sha256:…
  candidate_commit: "…"   # 集成收据必须绑定精确候选提交
  argv: [cargo, test, -p, parser]
  exit_code: 0
  required_checks: [parser.valid_frame, parser.invalid_frame]
  results: {parser.valid_frame: passed, parser.invalid_frame: passed}
  cleanup: confirmed
  log_ref: runtime/logs/T-4.a2.jsonl
```

新鲜度按收据**派生**，不另存可独立修改的事实：

| 派生状态 | 条件 |
| --- | --- |
| `FRESH` | 最新适用收据所有必跑检查通过、清理确认，且定义/计划/输入/代码/环境摘要与候选绑定均一致 |
| `STALE` | 旧收据曾通过，但任一摘要、作用域或候选绑定与当前不一致 |
| `DIRTY` | 无收据，或最近一次验证未通过 |

新鲜度按 `(任务定义, 检查作用域, 候选)` 分区，不能让旧候选迟到的失败污染新候选；同一分区内最近失败优先。仅对计划所要求的全部检查均满足时派生整体通过。结论只对记录的输入证据成立；硬件状态无法完全内容寻址时，每次重新初始化并验证，不跨运行复用硬件收据。工具链、命令、锁文件或隔离策略变化同样使旧收据失效。

#### 3.6.6 级联重算流程

规范变更按固定顺序处理：**校验封存提案并计算新图 → 保存不可变规范对象 → 追加接受事务并 fsync → 物化视图并发布调度版本**。派发只读取已提交版本；多文件物化与外部操作按 §3.3 恢复，不假设原子写入。

1. 比较新旧有效哈希映射，得到变更条目集合（新增、修改、删除均视为变更）。
2. 沿规范边求有效哈希变化，并沿产物边建立潜在受影响闭包；潜在可达不等于立即重派全部任务。
3. 按拓扑序及以下优先级处理：
   - **规范/任务目标/验收计划失效或权限收窄**：正在运行的按 §3.3 终止并采集，携带新定义重派；同样的代码摘要不能覆盖控制依赖变化。
   - **仅源码、上游产物或普通工具链输入漂移**：旧收据失效，但允许活跃 Worker 在冻结基线上结束。保存候选，将其代码增量三方应用到最新已接受基线后重新完整验收；有冲突或验证失败才派发修复。禁止把每次无关主干提交都变成全体 Worker 重启。
   - **仅产物边潜在影响且摘要未变**：上游接受后按实际读集与边模式比较；所有其他输入均有效时复用对应局部结果。组内候选传播遵循 §3.5 的冻结版本规则。
4. 接受新产物后按当前接受树发布 `artifact_digest` 与 `public_digest`。任何任务修改已有声明产物，都更新该路径相关产物索引与消费者，不能一直拿原生产任务的历史提交作当前摘要。按 §3.6.7 决定局部截断，完整集成验收始终执行。

队列有失败预算与公平性约束：单元受阻时只阻塞其依赖者；与其无依赖的就绪单元可在最新接受基线上继续排队。接口迁移使用显式集成组，不能让一个永远失败的队首阻塞全项目。

**示例**：`A-1` 的波特率由 115200 改为 921600。

| 节点 | 关系 | 处置 |
| --- | --- | --- |
| `A-1` | 变更源头 | 内容哈希改变，有效哈希改变 |
| `IF-3` | `depends_on: [A-1]` | 自身内容未变，有效哈希改变 |
| `T-2`（串口驱动） | 读集含 `A-1` | 直接命中：中断、重置、携带新值重新派发 |
| `T-3`（串口测试） | 读集含 `A-1`、`IF-3` | 直接命中：同上 |
| `T-4`（帧解析器） | 读集含 `IF-3`、`T-2` | 直接失效：`IF-3` 的有效哈希已变，不能被 `T-2` 的接口摘要截断 |
| `T-8`（极坐标渲染） | 读集含 `IF-7` | 无关：有效哈希未变，不动 |

若另一次变更只调整 `T-2` 内部实现，规范条目与公开文件均未变，则 `artifact_digest` 改变、`public_digest` 不变。`T-4` 只有在接口读取边界已证明完整、源码及环境等其余输入未变时，才可复用仅依赖接口的局部分析/编译结果；它链接新实现后的行为测试与候选完整验证仍需运行。全量源码可读的默认模式不能作此截断。

**删除与引用完整性**

以下四类情况必须在**写入磁盘时**校验，而不是等到运行时才发现：

| 情况 | 后果 | 处置 |
| --- | --- | --- |
| 删除条目 | 引用者在遍历中找不到起点，静默漏算 | 删除即变更：所有引用者进入受影响闭包；悬空引用直接阻止派发 |
| ID 复用 | 旧读集与新条目哈希偶然匹配，产生假阴性 | 禁止复用，删除后保留 `retired` 标记与墓碑记录 |
| 依赖成环 | 遍历不终止，受影响范围等于全库 | 提交时环检测，拒绝落盘 |
| 实现身份冲突 | 同一目标下误创建重复实现，或将 mock 与生产实现混淆 | 按 `(contract, target, implementation)` 识别实现；允许历史/后继任务修改同一实现，并发仍受写集互斥约束 |

这四项检查的代价是与条目数量成正比的线性扫描，远低于事后排查的成本。

#### 3.6.7 早期截断

早期截断按**依赖边与验证作用域**决定，不以单个摘要推断行为等价。物理计算边界为：

```text
artifact_digest(T) = H(sorted_manifest(writes.public ∪ writes.private))
public_digest(T)   = H(sorted_manifest(writes.public))
```

`sorted_manifest` 对已接受快照中的规范化相对路径、文件类型/可执行位、文件字节内容摘要或链接目标做规范编码，包含声明模式与匹配集合，使新增、删除、重命名也改变摘要。声明范围内的必需生成产物须显式纳入，不以 mtime 或模型所称“等价”代替内容。跨边界符号链接必须拒绝或展开并纳入真实目标依赖。

基础版本只哈希文件，不承诺语言级 AST/ABI 等价分析。头文件、`.d.ts`、接口包中的注释变化也可能改变 `public_digest`；这会多算，但不漏算。C++ 模板、Rust 宏与其他携带实现的公开产物不享有“只有签名”的假设。

| 依赖/验证范围 | 摘要与截断规则 |
| --- | --- |
| 公开接口依赖，读取边界已证明完整 | 比较 `public_digest`；其余规范、源码与环境输入未变时，可复用仅涉及该接口的局部分析/编译结果 |
| 读取实现或完整产物的依赖 | 比较 `artifact_digest` 及其他真实输入；实现改动使其失效，即使只是注释也保守重验 |
| 链接、运行时行为与硬件验证 | 纳入完整实现/二进制和环境，不能用 `public_digest` 截断 |
| staging 候选完整验证 | 每个候选重新执行；收据绑定完整候选与前驱，不因接口相同而跳过 |

源码审计发现额外依赖、会话含更宽历史读集或存在独立规范变更时，接口摘要相同不能挽救该结果。`artifact_digest` 相同也只有在全部其他输入未变时才支持局部复用。此优化依赖可证明的读取边界，应在保守模式正确运行后逐步启用。

#### 3.6.8 散文的咨询通道

在仅注入语义视图的执行模式下，块外散文修改不触发重算；直接读取原稿的调用按 §3.6.4 记录原始字节依赖。忽略散文仍有两个产品风险：

- 人在散文里写下带约束力的话（例如“帧必须以 0xAA 开头”“不要再引入新的第三方依赖”），系统毫无反应，而人以为它已经生效；
- 散文修改反映的是**意图漂移**，而意图漂移恰恰是假设账本存在的理由。

因此散文进入**咨询通道**，而不是正确性通道：

1. 对块外散文中出现规范性语气（“必须”“禁止”“不得”“shall”“must”）的段落做静态检查并告警，对应 INV-10；
2. 在微检查点提示“有 N 处散文修改尚未进入账本”，提供让架构角色生成结构化提案的操作；通过导入后约束才生效。

这样既保住了“零浪费”，也避免了“人以为的约束”与“系统实际的约束”之间的裂缝。

#### 3.6.9 未声明读的兜底

§3.6.4 的读取边界与保守回退是正确性前提；以下措施用于发现遗漏，不能替代它们：

1. **字面指纹扫描**。假设值发生变化时（如 `115200 → 921600`），在受影响范围之外全库检索该字面量；命中未声明依赖的文件则记 `UNDECLARED_READ` 告警。对常量类假设非常有效，代价接近于零。
2. **完整候选验证与周期性干净重验**。每次合并运行完整验证，周期性在无增量缓存的干净环境检查构建可复现性；硬件按 fixture 复位。依赖图可节省模型调用与有证据支持的局部重复验证，不能跳过候选集成验证。测试覆盖不等于依赖证明，全绿也不能证明隐藏源码依赖不存在。

#### 3.6.10 提交时校验清单

规范提交前必须通过以下检查，任一失败即拒绝写入：

| 检查项 | 目的 |
| --- | --- |
| 条目 schema 合法 | 保证可解析 |
| ID 唯一且未在墓碑列表中 | 防止 ID 复用 |
| 语义投影字段齐备 | 保证哈希可计算 |
| 引用完整（`depends_on`、`inputs`、`implements` 均可解析） | 防止悬空引用 |
| 无环 | 保证遍历终止 |
| 实现身份与构建目标合法 | 允许串行后继任务、不同目标实现与 mock，不使用全局任务引用唯一性 |
| `writes.public/private` 分类完整且不重叠，路径与上游产物选择合法 | 明确摘要与写隔离边界 |
| `resources` 可解析，资源别名归一，验证命令具备超时与清理策略 | 防止设备争用与孤儿进程 |
| `mode: public` 有可实现的读取边界或完整审计方案 | 无证据时按 `full` / 保守源码快照处理，不启用接口截断 |
| 任务目标、交付类型、变更策略及验收计划完整 | 防止改目标不失效、空 diff 误判和零检查通过 |
| 集成组成员、内部依赖、目标规范与预算合法 | 防止跨任务迁移死锁与无限合并批次 |

无引用接口、规模异常、可疑散文等是规划告警，不与 schema/引用损坏混作硬性拒绝；缺少优化能力时采用声明过的保守模式，缺少必要隔离能力时才拒绝派发。

## 4. 协同拓扑与闭环流转

### 4.1 角色分工

| 角色 | 定位 | 推荐模型 | 输入边界 | 核心职责与约束 |
| --- | --- | --- | --- | --- |
| **架构统筹** | 需求解析与调度 | 强/慢 | 原始需求、目录树、验证结果、契约摩擦报告、假设账本 | 按需唤醒。产出极简契约与切片任务；**只提交变更提案，不直接写盘** |
| **核心构建** | 业务与底层逻辑 | 快/廉价 | 单任务描述、读集条目、1~2 个直接关联源文件 | 遵循契约实现功能；探索期禁止防御性代码与过度抽象；契约不可行时提交 `contract_friction` |
| **测试与工具** | 验证与仿真 | 快/廉价 | 读集条目、运行环境与硬件规范 | 与核心构建并行。依据契约编写测试、Mock 与模拟器；新增测试作为补充，不能修改受保护的最低验收标准 |
| **对抗性审查** | 冗余与偏离检查 | 强/慢 | 差异集、读集条目、集成日志 | 条件触发（见下）。输出结构化裁决，不通过则附精简指令打回 |

**审查角色的触发条件与评价标准**

每轮都让强模型阅读全量差异会占据主要成本，且“是否过度设计”本身主观。改为条件触发：差异超过 N 行、出现新文件、新增依赖、跨任务边界、到达检查点。

评价标准必须可判定，例如：是否修改了写集之外的文件？是否引入只有单一调用者的新抽象？是否新增契约中不存在的依赖？差异规模与任务声明规模之比是否异常？输出结构化裁决而非散文评论。

**接口一致性由可执行检查验收**。类型、签名等可机械检查的契约绑定编译/接口检查器；“非阻塞、1ms 内返回”等行为约束须绑定具体测试、测量环境与阈值。自然语言不能自动变成完整的测试 oracle，模型生成的测试先作为候选证据，经认可后进入验收计划。暂不可自动检查的要求显式设置人工验收项，不宣称“机器全绿”已经覆盖它；模型审查可发现语义风险，但不替代这些验收项。

### 4.2 失败分类与升级阶梯

“失败两次就换强模型”会把成本花在无效的地方。 Supervisor 的核心智能体现在这张路由表：

| 失败类别 | 处置 | 升级模型是否有效 |
| --- | --- | --- |
| 语法或编译错误 | 附带报错片段，同级模型重试 | 无效 |
| 测试失败且信息充分 | 附带日志尾部重试 | 通常无效 |
| 方向错误、误读契约 | 升级模型 | 有效 |
| 契约物理上不可行 | 架构角色修订契约 | 无效 |
| 环境漂移、认证过期 | 修复环境、重启进程 | **无效，会导致持续消耗** |
| 需求自相矛盾 | 转人工 | 无效 |

**升级先按失败类别路由**。仅模型可修复的任务错误走“附证据重试 → 更换策略 → 强模型修复”；环境/认证问题直接进入环境修复，契约矛盾直接进入规范提案，副作用结果未知直接进入核对。统一的预算上限不能被换模型或切类别重置。

**重试必须包含变化**。以相同提示词重跑是已知低效的做法。每次重试注入失败证据、Supervisor 保存的差异摘要与显式收敛约束（例如“上次修改了 6 个文件，本次限制在 2 个以内”）。Attempt 的恢复点由 Supervisor 固定到 `refs/orgy/attempts/<task>/<n>`，复用同一 Task 目录，不要求 Worker 自己提交或每次新建分支。合并队列失败还需附带前驱候选、完整验证收据与交互诊断，不能仅凭队列位置认定模型方向错误。

**预算与熔断**。Task、集成组与 DAG 都有调用次数、活动耗时及总等待期限；修复轮、被杀 Attempt、诊断和验证重跑均计入相应预算。启动前预留额度，结果出来后结算；超限暂停派发并给出下一步，不自动以更贵模型绕过额度。token 数据缺失时不能声称硬性限制 token 成本，以调用数/时间为硬上限，token 估算仅用于观测。等待人类期间释放物理资源，但不无限延长任务期限。

### 4.3 典型闭环

1. **需求对齐与切片**：人类输入需求 → 架构角色产出契约、假设、目标与验收提案 → Supervisor 导入为新规范版本 → 派发首个可验收切片。
2. **并行开发**：核心构建与测试工具在固定 Task 工作区并发执行（受写集与资源互斥约束）。进程卡死时终止并采集现场，再走 `one_for_one`；发现契约摩擦则挂起并唤醒架构角色；规范变更按规范和源码依赖证据重派受影响任务。
3. **集成验证与失败升级**：单任务或显式集成组形成候选后进入队列，按目标规范运行完整验收；接口迁移不得拆成无法独立通过的接受步骤。失败保留已接受前缀，按 §3.5 诊断与 §4.2 分类处置。
4. **审查与微检查点**：条件触发审查 → 基线未变且验证有效时按队列顺序晋升精确候选 → 展示阶段成果，等待人类确认方向或修改假设。检查点只提供三个动作：**接受方向 / 修改假设 / 中止重规划**。

## 5. 非目标

- **不内置任何大模型 SDK 或 API 客户端**：完全复用用户本地已配置登录态与环境的 CLI 工具。
- **不构建封闭格式**：规范、提案和状态使用可读文本；人类可用任意编辑器修改提案，已接受状态通过导入/API 修改。运行时日志与派生视图可读但不可手工改写，不产生第二份事实源。
- **不追求无人值守**：坚持微检查点与假设账本，将人类保留在关键决策回路上。
- **不自研终端模拟器，不承诺运行中接管**：PTY 仅用于诊断与人工处理，且“接管”是重新拉起而非附着（§3.1）。
- **不依赖表象层做正确性判断**：这是 §2.3 的直接推论，也是本架构不把终端输出或事件名当作状态来源的依据。

## 6. 实施路线与验收指标

### 6.1 引擎里程碑

- **M0 单平台正确性闭环**：选一个可证明隔离与父死回收的平台后端，单 Worker、固定 Task 目录、一个交付适配器、受保护验收计划、不可变候选、OS 单实例锁、追加日志与意图/结果恢复、硬预算和快照。使用保守读集与全量验证，不含 DAG、PTY、共享缓存或日志裁剪；未实现的能力明确拒绝使用。
- **M1 治理与持久化**：提案导入、规范版本发布、检查点/GC、能力探针、私有临时与会话区、无凭证验证 helper、强制代理出口。按实际目标添加平台后端；涉及硬件前先实现资源与动作执行边界。
- **M2 并发与集成**：写集/资源租约、构建配置单写者、串行合并队列、显式有界集成组与故障归因。投机队列、共享编译缓存和多主机设备池推迟到有实测收益后。
- **M3 增量优化**：在已有规范版本和全量正确性路径上，引入有效哈希、生成/验证读集分离及局部结果复用，按 §6.2 分期实现；不将完整文件审计列为首版前提。

### 6.2 增量重算分期

依赖图本质上是自研一个微型增量构建系统（与 Bazel、Buck 的缓存失效机制同源）。按本文档的原则，它也应渐进引入，每一期都要明确收益门槛：

| 阶段 | 内容 | 代码量级 | 值得引入的条件 |
| --- | --- | --- | --- |
| **S1** | 条目化 + 规范有效哈希 + 保守源码快照 + 线性失效 + 一律重验 | 小 | M0 正确性闭环稳定后引入，默认禁用接口级截断 |
| **S2** | 正向闭包、拓扑序、“先重验后重写” | 中 | 并行任务达到三个以上，级联开始成为瓶颈 |
| **S3** | 受限视图/完整审计 + `public_digest` / `artifact_digest` 按边截断 | 中至大，依平台而异 | 读取边界已验证且局部重验成本显著；始终保留完整候选验证 |
| **S4** | 字面指纹告警 + 周期性干净重验与审计覆盖检查 | 小至中 | 作为附加诊断逐步引入，不能替代 S1/S3 的读集保证 |

判断原则可以直接量化：**若一次全量重验只需数分钟，而维护依赖图的成本是数周，则先做全量重验**。增量优化必须建立在完整输入证据上，验证器提供验收证据；二者都不应被解释为对任意运行行为的证明。

### 6.3 验收指标

“高鲁棒”必须可度量，否则无法验收。建议跟踪：

- `CLAIM_MISMATCH` 率（声明产物与实物不符）与 `VALIDATION_FAILED` 率（验收不通过）分别统计；
- `KILLED` 误杀率（被终止后经确认实际仍在正常工作的比例）；
- `PROTOCOL_ANOMALY` 率；
- 每任务平均尝试次数；
- 每任务人工干预次数；
- 合并冲突次数。

此外用故障注入和场景验收覆盖：

- 两个 Supervisor 同时启动只允许一个持锁；草稿多文件修改不能半批生效；日志中段损坏不得继续调度。
- 检查点发布、进程启动与 Git CAS 前后分别强杀 Supervisor，恢复后不重复启动、漏认晋升或丢失动作意图；旧执行实例未回收前不复用目录/设备。
- 正常退出的澄清、只读审查和合法空 diff 可路由；超时、协议修复、诊断重启不能绕过预算。
- 改目标/验收计划必须失效，数字与字符串不误合并；自身修改不造成自失效，无关源码合入不使全体 Worker 重启。
- 驱动接口与消费者同步升级可整组验收；前驱失败使投机结果作废；候选修改测试或输入树不能伪造受保护验收通过。
- 同板别名不能并发，原始设备权限不能绕过授权执行器；动作结果未知不自动重试；代理直连被阻断，验证器无模型/推送凭证。
- 抢占后无交付物仍可采集恢复、固定路径续接失败可降级、只读角色可写临时状态；代码实现变化仍执行完整集成，验证结束无存活孙进程。

指标按工具故障、任务失败、输入失效与取消分组，不能将一次规范变更造成的主动终止计为模型失败，也不能通过排除被杀调用来美化总成本。

## 7. 已定默认值与待决问题

默认设计已确定：Task/候选独立构建目录、受控下载内容与可选编译缓存；终止后采集；outbox/定界符降级交付；规范提案独立导入；冻结验收计划和候选；单任务优先、必要时有界原子集成组。首版不以多平台、投机队列或完整访问审计为前置条件。

仍需实测或进一步设计的事项：

1. **缓存后端与容量**：`sccache` / `ccache` 的适用工具链、命中率、配额和淘汰策略，以及 CoW 克隆在各平台的收益。
2. **进程清理参数**：各工具的退出清理时限、强杀后的句柄释放等待、现场采集上限；它们不是等待 `PREEMPTED` JSON 的宽限期。
3. **适配器兼容性**：各工具版本的最终消息边界、定界符交付成功率、状态目录配置与续接行为；不通过探针的能力不得投入调度。
4. **平台后端选择**：首个落地 OS/服务管理器及其 flush、owner-death 回收、代理出口与受限文件视图能力；完整审计和其他平台后续加入，不能把未实现能力标为已支持。
5. **审查与合并队列参数**：差异行数、文件数、依赖增量阈值，投机队列深度和偶发失败诊断预算。
6. **跨主机硬件资源**：公共租约服务、设备别名注册、断连后的复位与隔离流程。
7. **范式命名与跨仓库规范**：“进程与产物契约优先”的最终措辞，以及跨仓库稳定 ID、版本与依赖图组织。
8. **验收与迁移规模**：各语言的受信 runner、基线检查固定方式、人工验收项，以及集成组大小/耗时上限与兼容迁移模板。

| 二-4：硬件与环境资源 | **采纳**。引入 `resources` 与统一租约，覆盖 Worker 和验证器；补充设备别名、同板串口/JTAG 联动、复位和跨实例协调，资源锁不替代副作用授权。 | INV-6、§3.5、§3.6.2 |
| 三-1：域名白名单落地 | **采纳代理出口，修正网络前提**。代理变量本身无隔离力，完全断网也无法到达代理，必须有唯一受限通道并阻断直连。HTTPS 隧道目的地过滤不等于内容审计，模型推理连接也需显式授权。 | 架构图、§3.4 |

| 四-2：无 schema 交付 | **采纳**。授权 outbox 或带本次 nonce 的唯一完整封装，不要求 stdout 全为 JSON；仍需限长、身份/schema 校验、修复轮与客观验证。 | §3.1、§3.2、§7 |
| 四-3：验证命令与孤儿进程 | **采纳并补足进程边界**。参数数组、允许命令、超时、空 stdin、每条命令完整进程回收；Unix 进程组本身不能阻止脱离会话。幂等性另靠可重建工作区与 fixture 复位保证。 | INV-7/8、§3.2、§3.5、§6.3 |

## 9. 二次设计审查与修订（2026-11-14）

本轮保留版本号 `0.2.0`，直接修订正文。下表按问题列出原因、具体后果与解决方式；P1 为影响正确性/可恢复性的机制缺口，P2 为明显的活性、兼容性或实施成本问题。

| ID / 级别 | 问题与原因 | 后果 | 已落实的修订 |
| --- | --- | --- | --- |
| R1 / P1 | `spec/` 同时允许人类编辑与 Supervisor 写入；去抖和 `base_hash` 无法消除检查后的覆盖窗口。PID 文件也不是排他锁。 | 人类修改被覆盖、多文件半批生效，或两个 Supervisor 同时改日志/发资源。 | 独立 `drafts/` 批次封存导入，规范只从不可变已接受版本发布；按仓库身份持有 OS 锁，默认禁止跨主机共享运行态（INV-1、§3.3）。 |
| R2 / P1 | 删除旧 journal 后仍把唯一快照当作可丢弃；截断规则未区分尾撕裂与中段损坏。 | 快照损坏后无从恢复，预算/副作用事实可能丢失，损坏被误当正常重放。 | 区分派生快照与持久检查点，保留链锚点/上一恢复代际/引用对象，仅丢弃未提交尾部，中段损坏停止派发（INV-4、§3.3）。 |
| R3 / P1 | 日志 fsync 不能与 spawn、Git ref 更新或设备动作组成原子事务。 | 崩溃后重复执行、漏认已晋升候选，甚至再次烧录；移动用户检出分支还会使索引与文件脱节。 | `operation_id` 意图/执行/结果及事实对账；Git CAS、受管接受 ref、独立规范/代码版本；未知外部结果挂起，不承诺通用 exactly-once（§3.3、§3.5）。 |
| R4 / P1 | cgroup/进程组不会随 Supervisor 死亡自动清空，Job 也未定义 kill-on-close 与入组时序。 | 父进程强杀后旧 Worker 继续写文件/占板卡，新实例误复用现场。 | Windows 创建时原子入组或独立启动所有者覆盖窗口；Linux 外部回收后端；重启先对账回收，缺能力时隔离而不自动续跑（INV-8、§3.4）。 |
| R5 / P1 | L1/L2 路由缺组合和跨字段约束，空 diff 一律失败，结构修复及被杀调用预算不明确；观测/交付解析混同。 | 正常澄清或只读审查无法完成，完成声明可能同时包含阻塞问题，修复/诊断反复调用不计成本。 | 完备优先路由、状态/阻塞字段一致性、交付类型和变更策略、受限修复、全部调用计预算；观测失败与交付失败分别处理（§2.3、§3.1、§3.2、§4.2）。 |
| R6 / P1 | 任务目标仅在被忽略的 `title` 中，验收计划缺版本；无条件把字符串数字归一；忽略的散文仍可能被模型读到。 | 改为“带校验的解析器”仍复用旧结果，类型变化或隐式文本指令不触发失效。 | 增加 `objective/acceptance` 与控制依赖；默认保留类型、哈希规则版本化；执行视图只注入语义字段，原稿读取则记录字节依赖（§3.6.2—§3.6.5）。 |
