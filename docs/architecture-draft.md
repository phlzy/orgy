# ORGY 核心架构与协作范式

**O**pen-ended **R**esilient **G**enerative **Y**ard

**Status:** 草案 `0.3.0`

**Date:** 2026-11-14

---

## 摘要

ORGY 是一个服务于**个人、单用户、单机**软件与异构硬件开发的多智能体编排工具。一个本地 Supervisor 调度多个 Worker 和本机连接的设备；不建设多用户或跨主机协调系统。它不封装大模型 API，而是通过子进程、文件系统、Git 与现有沙箱能力驱动用户配置好的终端 AI 工具，把不同模型组织成可验证的研发流水线。

本草案给出的设计分为三层：

- **执行层**：以一次性 headless 子进程为主路径，把交互式终端（PTY）降级为诊断与人工处理的通道；
- **状态层**：人类直接编辑规范，显式发布 Git 快照；Supervisor 用本地 SQLite 保存运行态，文本审计只是导出视图；
- **规范层**：在人类可读的 Markdown 中嵌入机器可解析的条目，由条目依赖关系计算增量重算范围。

贯穿三层的是十条**核心状态不变量**（§2.4）。它们是本架构的地基，每一条都附带客观的检测方式——不可检测的约定不纳入不变量。

建议的阅读顺序：§2（原则与不变量）→ §3.2（三层判据）→ §3.3（状态层）→ §3.6（语义化规范层与增量重算）→ §4（协同拓扑）。

## 术语表

| 术语 | 含义 |
| --- | --- |
| **Supervisor** | 唯一的本地编排进程，写运行态与受管 Git refs；不在后台改写人类的 `spec/` 工作副本 |
| **Worker** | 由 AI 工具进程承担的一次性执行者，无持久状态 |
| **任务（Task）** | 具备明确验收条件的可验证工作单元，通常对应一个最小垂直切片 |
| **会话（Session）** | 工具自身的对话状态，可跨多次进程调用续接 |
| **尝试（Attempt）** | 一次 headless 子进程调用。粒度最细，可随时丢弃 |
| **条目（Entry）** | 规范层中带稳定 ID 的机器可解析单元，如一条假设、一条接口、一个任务定义 |
| **语义投影** | 条目中真正具备约束力的字段子集，用于计算内容哈希 |
| **内容哈希** | 仅覆盖单个条目语义投影的指纹 |
| **有效哈希** | 条目自身内容哈希与其依赖条目有效哈希共同滚动的指纹（§3.6.3） |
| **注入清单** | 派发任务时实际注入 Worker 上下文的条目及其哈希，构成规范读集；源码读取另行记录 |
| **读集 / 写集** | 规范条目、源码与构建输入的依赖集合 / 任务声明可写的路径集合（公开与私有产物之并集） |
| **验证收据（receipt）** | 一次验证的完整凭据：输入、代码、环境摘要与结果 |
| **爆炸半径** | 某条目变更后需要重算或重验的任务集合 |
| **早期截断（early cutoff）** | 按依赖边的摘要与读取边界复用结果；公开接口摘要相同不代表运行时行为相同 |
| **表象层（surface）** | 第三方工具的消息格式、终端渲染等无兼容性承诺的呈现形式 |
| **暂存区（staging）** | 按合并队列构造候选提交并运行完整验证的隔离工作区 |
| **集成单元（integration unit）** | 可独立通过验收的单任务，或显式声明、整体晋升的有界任务组 |

## 1. 项目愿景与问题陈述

### 1.1 定位

ORGY 的目标不是重新实现一个 AI 编程助手，而是解决**已有多个 AI 编程助手之后**的问题：如何让它们并行、可验证、可恢复地协同，并且让人类始终掌握方向。

因此 ORGY 明确站在工具之上而非之下：它不实现推理调用，也不建立自己的长期模型凭证库；启动工具时可使用用户授权的凭证句柄或最小环境，负责编排进程、约束环境、收集产物、执行验证、记录事实。

本项目首先防范误操作、并发冲突和工具崩溃；默认用户信任自己的工具链及项目脚本，不把本机视为对抗恶意同权限进程的多租户系统。采用现有权限能力保护主工作区与运行态，不自研跨平台沙箱。验证证据的保证范围须明确记录，不能把较弱的终态检查说成过程隔离（§3.4）。

### 1.2 需要解决的四个问题

1. **工具链割裂**：多个终端窗口各自为战，缺乏上下文同步、文件并发控制与统一的验证闭环。人类的判断散落在多个会话里，无法回溯。
2. **能力与成本错配**：快而廉价的模型容易陷入循环或缺乏全局视角；强而昂贵的模型响应慢、成本高，不适合承担大量样板代码与测试编写。二者的分工需要由系统而非人脑来维持。
3. **进程脆弱性**：第三方 CLI 工具在长任务中可能因网络波动、上下文压缩或终端渲染异常而卡死。任何“等它自己好起来”的策略都不可靠。
4. **需求模糊与过度设计的矛盾**：用户初期目标往往不完整；若让 AI 提前做详尽架构设计，又会产生大量僵化的防御性代码，导致后期难以转向。

### 1.3 由此导出的设计约束

| 问题 | 设计约束 |
| --- | --- |
| 工具链割裂 | 规范为可编辑文本，运行态用单写者 SQLite，提供可读导出 |
| 能力成本错配 | 角色与模型级别必须解耦，且支持按失败类型升级 |
| 进程脆弱 | 执行者必须可随时丢弃，记忆不能驻留内存 |
| 过度设计 | 校验必须由机器完成，人的介入点必须少而关键 |

## 2. 设计原则

### 2.1 状态与执行解耦

借鉴 Erlang/Elixir 的 Actor 模型与监督树（supervision tree）：系统的“记忆”放在磁盘上，“算力”放在可丢弃的进程里。进程崩溃是正常事件，不是需要防御的异常。

在实现这套模型之前，必须先把三个层级分清，否则“容错”会退化为“反复重来”：

| 层级 | 生命周期 | 载体 | 丢弃代价 |
| --- | --- | --- | --- |
| **Task** | 跨多次尝试 | `spec/tasks/<id>.yaml` 与运行时状态 | 高：需要重新规划依赖 |
| **Session** | 跨多次 Attempt | 工具自身的会话存储（如 `codex exec resume`、`dsh --resume`） | 中：丢失模型已建立的理解，重试时需重建上下文 |
| **Attempt** | 单次子进程调用 | 一次性 headless 进程 | 进程可丢弃；终止前后仍需保全磁盘现场与副作用记录 |

由此得到两条操作：

- `restart(process)`：旧进程树确认退出并保存现场后，复用 Task 的固定 CWD 与会话目录；仅在适配器探针确认支持续接、会话可读且上下文仍适用时续接。工作区发生变化时注入变更说明；工具不支持续接或会话损坏时开启新会话。
- `reset(context)`：方向错误、上下文污染或输入失效时开启新会话，注入最新契约与 Supervisor 保存的恢复摘要。是否保留代码现场由显式恢复策略决定，重置会话不等于自动清空代码。

会话定位是否依赖 CWD 是工具与版本相关的能力，不能一概而论。固定 Task 路径降低兼容风险，但不能替代续接探针与输入校验；同一 Task 的 Attempt 始终串行（§3.5）。

把两者混为一谈，会让系统在每次重试时都从零开始理解代码，既昂贵又健壮性更差。

**监督树策略**：

- `one_for_one`（局部自愈）：单个 Worker 卡死或偏离任务时，仅重建该次尝试，不影响同级并行任务。
- `rest_for_one`（级联重置）：规范条目演进后，仅重建**读集中包含受影响条目**的下游任务（§3.6.4）。这里的关键是“仅”，否则级联重置等同于全量重启。

### 2.2 渐进式探索与契约演进

- **最小活体切片（tracer bullet）**：初期禁止复杂抽象与防御性代码，优先用最直白的实现端到端跑通一条可观测链路（例如“串口收到指令 → 点亮 LED → 返回状态”）。目的是尽早暴露目标偏差，而不是尽早完成代码。
- **契约即边界**：模块之间只通过极简的接口契约解耦，使主逻辑与测试/仿真可以真正并行。契约必须**同时是人类可读的散文与机器可解析的条目**（§3.6），否则并行安全性与 mock 自动生成都无从建立。
- **契约双向演进**：底层执行者发现契约矛盾时输出 `contract_friction` 并挂起；架构角色提出修订建议，用户审阅、修改规范并 apply 后，才触发受影响下游重算。
- **假设显性化**：用户未说明的需求盲区必须显式记入假设账本（带稳定 ID 与默认值），而不是默默写死在代码里。Worker 必须声明本次实际使用了哪些假设，使“隐含猜测”变成可审计的数据。

### 2.3 正确性不依赖第三方表象

这是本设计最基础的一条原则：

> **正确性只依赖三样东西：进程退出状态、磁盘产物、ORGY 自己的验证器。**
>
> 终端屏幕内容、ANSI 控制序列、JSONL 事件名称、提示符样式，均属于**表象层**，只能用于延迟优化、进度展示、成本统计与故障诊断。

理由：屏幕渲染和事件名称都是第三方工具的实现细节，没有任何兼容性承诺。把系统正确性建立在它们之上，等于把可靠性寄托在别人一次 UI 重构上。

这条原则适用于进度、心跳与用量等 JSONL 观测事件：解析失败只降低观测精度。最终交付物是 ORGY 主动要求的协议输入；若某工具必须从事件中提取最终消息，该适配器也是交付链的一部分，解析失败须明确记为协议异常并降级到文件交付，不能声称对判定完全无影响。任何一种文本都不能代替 L3 验收。

### 2.4 核心状态不变量

以下十条不变量是引擎的地基。每条都给出客观检测方式，因为无法检测的约定在实现中一定会退化。

| ID | 不变量 | 检测与处置 |
| --- | --- | --- |
| **INV-1** | **运行态单写者、人类掌管规范**：Supervisor 唯一写数据库与受管 refs，人类直接编辑 `spec/`；AI 只交提案 | 按仓库身份持有本机 OS 排他锁；`orgy apply` 经该实例提交。运行期只读已发布 Git 快照，不监视/回写人类规范文件 |
| **INV-2** | **写权限显式授予**：Worker 仅可写声明的源码路径及专属临时、会话、构建与 outbox 目录；交付只经授权通道 | OS 沙箱限制路径；Supervisor 对比 Git 差异与未跟踪文件，越界记为 `SCOPE_VIOLATION`。Git 检查不代替对仓库外写入的阻断 |
| **INV-3** | **快照冻结**：Worker 侧 `spec/` 在一次 Attempt 内固定为派发快照，绝不回流主干 | 候选规范只能由 Supervisor 物化为目标 `spec_revision`；Worker 代码增量不得包含规范文件 |
| **INV-4** | **数据库事务权威**：运行态以 SQLite 已提交事务为准，外部动作仍需意图与结果对账 | WAL/FULL、外键和唯一约束维护数据库一致性；审计文本不能反向恢复状态；异常时停止派发并恢复备份或对账 |
| **INV-5** | **语义与源码输入分开**：规范失效以结构化约束为准，说明文本保存为上下文来源；源码按全量快照或物化检查文件集记录 | 语义哈希、源码和工具环境分别比较；不追踪系统调用。仅受限文件集中的局部检查可使用接口级复用，不能据此证明模型未读其他代码 |
| **INV-6** | **写集与本地资源互斥**：并发任务不得具有相交写集或占用同一设备 | 唯一 Supervisor 检查路径和 `resources`，用本地占用表调度；不需要分布式租约或 fencing |
| **INV-7** | **验证者权威**：按用户发布的计划验证候选，自报仅为声明，收据记录实际隔离等级 | 对账实际检查集合、候选输入和终态差异；默认信任本地脚本，不宣称前后哈希能证明执行期间从未改动源码 |
| **INV-8** | **无孤儿复用**：执行实例有本机进程回收边界，全部进程确认退出后才释放占用 | Windows 使用不可继承控制句柄与 kill-on-close Job；其他平台复用已有回收能力。清理未确认则隔离现场，不假定父进程退出就代表子进程已死 |
| **INV-9** | **不可逆副作用需事前授权**：烧录、推送、删库等动作经受控执行边界放行 | 授权绑定动作、目标、参数、产物摘要与有效期；持久化执行意图及结果。结果未知挂起对账，不能自动重复执行 |
| **INV-10** | **正式约束显式发布**：要求写入结构化条目与验收计划；散文帮助理解，不自动成为验收标准 | `orgy apply` 展示语义与说明差异，关键词检查仅提示，不能证明自然语言没有新要求（§3.6.8） |

## 3. 系统架构

```text
+---------------------------------------------------------------------------------+
|                     Human-in-the-Loop TUI / CLI                                 |
|   [任务看板]      [人类编辑 spec/；AI 提案 drafts/]    [诊断与手工处理]           |
+-----------------------------------+---------------------------------------------+
                                    | 人类保存后 orgy apply；无后台文件监视
+-----------------------------------v---------------------------------------------+
|                    ORGY Core（Supervisor，唯一写者）                             |
|  +--------------+  +--------------+  +--------------+  +------------------+     |
|  | 调度与状态机  |  | 传输适配器    |  | 客观验证器    |  | 策略与权限引擎    |     |
|  | 增量重算/预算 |  | exec/JSONL   |  | build/test   |  | env/sandbox/探针  |     |
|  +--------------+  +--------------+  +--------------+  +------------------+     |
+----+-------------------------+--------------------------+----------------------+
     | SQLite 事务           | 本地进程回收                | Git CAS 操作
+----v-----------------+  +----v----------------+  +------v--------------------+
| .orgy/spec/   [Git]  |  | Worker 进程树      |  | worktree 池与暂存区        |
| .orgy/runtime/[忽略] |  | 一次性 Attempt     |  | /worktrees/<task>         |
| - state.db（权威）   |  | stdin : prompt     |  | /worktrees/staging        |
| - audit.jsonl（导出）|  | stdout: JSONL 事件 |  | 写集互斥（INV-6）          |
| - logs/              |  | exit  : 传输层事实 |  | 本地占用与回收（INV-8）    |
+----------------------+  +--------------------+  +---------------------------+

依赖准备 helper --> 联网预取与锁定 --> 本地包缓存 --> 离线构建/验证
模型 CLI --> 用户配置的模型连接；不因离线构建而断开推理服务
副作用请求 --> Supervisor 的本地授权命令入口 --> 指定设备或服务
```

### 3.1 执行层：结构化主路径，PTY 仅作兜底

**主路径：一次性 headless 子进程**

针对支持非交互模式的 CLI 工具（`codex exec`、`dsh --profile headless` 等），ORGY 作为父进程，通过标准输入注入提示词、消费标准输出的事件流、以退出码作为**传输层**的硬边界。

- **确定性生命周期**：退出码与终止信号是“进程如何结束”的唯一事实来源。它不回答“任务是否完成”，但消除了“根据屏幕停滞猜测状态”带来的不确定性。
- **事件流仅作观测**：事件映射为进度心跳与成本统计，由工具适配层按版本解析（§3.4 的能力探针会记录事件格式指纹）。工具若在事件中报告 token 用量则顺带采集，不支持则标记为未知，不做任何正确性假设。
- **双管道持续排空**：stdout 与 stderr 并发独立读取，避免 stderr 缓冲区满使 CLI 假卡死。日志达到上限后截断存储但继续读取，解析器错误不得停止排空；最终交付使用独立有界缓冲或 outbox，不能被普通日志轮转吞掉。
- **强类型交付**：通过 `--output-schema` 或等效手段约束最终消息符合 JSON Schema（§3.2）。这取代自由文本交接日志，使“完成 / 需要澄清 / 受阻”成为可路由的枚举，而不是需要人（或模型）去解读的一段文字。
- **交付通道优先级**：优先使用工具原生 schema 与最终消息提取能力；缺少该能力时使用授权 outbox 或定界符封装（见下）。架构与审查角色是**代码库只读**，仍有专属临时、会话与 outbox 写权限，输出提案由 Supervisor 校验后落盘。
- **长提示词走标准输入**：Windows 的 `cmd.exe` 限制约 8K 字符，直接创建进程也有长度限制；命令行参数还可能出现在进程列表中。以参数数组直接启动，不经 shell 拼接；注入后允许关闭 stdin，不把它假定为运行中的控制通道。

**无 schema 能力时的交付降级**

- 支持文件输出的工具写入本次专属 `.orgy/outbox/<task>.a<n>.handoff.json`；Supervisor 在进程树退出后有界读取，拒绝符号链接、越界路径及不匹配的 Task/Attempt 标识。
- 否则要求最终回答以 `<<<ORGY_HANDOFF_START:<nonce>>>` 与 `<<<ORGY_HANDOFF_END:<nonce>>>` 包裹 JSON。适配器只从本次最终消息提取；无最终消息边界时，从有界捕获输出中接受唯一完整、带本次随机 nonce 的封装，缺失、多份或截断均视为协议异常。nonce 用于避免误匹配，不是认证凭据。
- stdout 可以包含 banner、日志或 JSONL，不要求整个流是纯 JSON。提取后仍做大小限制、JSON Schema 校验、身份对账与客观验证；失败只允许一次结构修复轮。原生 schema 也不保证内容真实。

**降级路径：PTY 用于诊断与人工处理**

PTY 的触发条件必须收窄，并区分两类性质不同的情况：

| 类别 | 含义 | 处置 |
| --- | --- | --- |
| **工具级异常** | 认证失效、许可确认弹窗、未知 CLI 报错、工具崩溃 | 按预算启用 PTY 诊断；仅进度事件畸形不触发重跑 |
| **任务级失败** | 编译错误、测试失败、模型偏离任务 | 进入重试与升级阶梯，**不启用 PTY** |

区分两者很重要：测试失败是非零退出的常态，若把它当作“异常”而进入诊断路径，系统会在最常见的情况下退化回屏幕解析。

PTY 兜底应产出**诊断包**：最近 N KB 原始输出、探测到的弹窗文本、可复现的命令行、环境差异。出路只有两条：

1. 弹窗文本命中工具配置中**预先声明**的允许项时，可自动应答；
2. 其余情况挂起等待人类处理。

不允许从屏幕内容推导出授权决定——那等于把安全策略交给第三方 UI 的措辞。

仅进度事件解析失败时继续采集原始输出，不自动重跑任务。PTY 重拉起是新的、有预算的执行实例；先终止并采集旧实例，使用同样的权限和副作用边界，不能为了诊断自动重复已经可能执行过的外部动作。

**关于“实时接管”的语义澄清**

Windows 无法为一个已存在的进程补挂 ConPTY；类 Unix 系统也需要 tmux/screen 一类复用层才能做到。因此“接管”在工程上只能是 **同环境重新拉起**（respawn with same environment），而不是附着一个正在运行的进程。

本架构不承诺热接管，只承诺交付“可复现命令 + 诊断包”，由人类在自己的终端中继续。这样做的代价是失去运行中的实时干预能力（列入非目标），收益是不必维持一个常驻的伪终端多路复用层。

### 3.2 三层判据与出口路由

任务结论不能由单一信号判定。三层判据如下（对应 INV-7）：

| 层 | 信号 | 回答的问题 | 权威性 |
| --- | --- | --- | --- |
| **L1 传输层** | 退出码、终止信号、是否因超时被终止 | 进程是正常结束还是异常终止 | 硬事实 |
| **L2 协议层** | 交付物的 `status` 与证据字段 | 模型**声称**自己处于什么状态 | 声明，不可采信 |
| **L3 验证层** | Supervisor 自己执行的构建/测试、自己计算的差异 | 客观结果是否成立 | **唯一权威** |

**完成判定**：L1 正常 ∧ L2 为 `COMPLETED` ∧ 该交付类型的 L3 验收全部通过 ∧ 声明与实物一致。代码类完成还需对应集成单元被接受；只读分析、规范提案与审查按各自验收器处理，不能统一要求存在代码 diff。

| L1（按优先级匹配） | L2 交付物 | 处置 |
| --- | --- | --- |
| 被终止、超时或资源违规 | 任意 | 记录取消/超时/隔离原因，终止并采集现场；不接受成功声明 |
| 正常 | 合法 `COMPLETED` | 按 `deliverable_kind` 对账与验收；越界为 `SCOPE_VIOLATION`，声明与实物不符为 `CLAIM_MISMATCH`，验收失败为 `VALIDATION_FAILED` |
| 正常 | 合法 `BLOCKED` / `NEEDS_CLARIFICATION` | 先核查契约摩擦与账本，再修环境、补输入或批量升级；不记为模型失败 |
| 正常 | 缺失或非法 | 一次只修结构的调用，绑定原产物且禁止改代码；仍失败记 `PROTOCOL_ANOMALY` |
| 非零 | 任意 | 不能直接接受成功；先按适配器、退出事实与环境探针诊断，合法阻塞声明仅作线索。可恢复产物经新的受控完成流程重新验收 |

非零退出的 stderr 特征仅辅助分类，不单独决定授权或任务完成；分类不明则 `TOOL_FAILURE_UNKNOWN`，按预算有限重试或转人工。修复轮、诊断重拉起、被终止及失败调用都计入 Attempt/耗时总预算，故障类别可分开统计。

`deliverable_kind` 由 Task 指定并由 schema 判别：`code_change` 提交代码，`spec_proposal` 提交条目操作，`review` 提交结构化裁决，`analysis` / `verification` 提交报告或验证请求。代码任务的 `change_policy: required | optional | forbidden` 决定空 diff 是否允许；需求已满足时可按 `optional` 验证后完成，Worker 不能自行更改策略。规范提案通过导入验证、审查裁决通过策略校验都不等于代码已经通过集成。

**交付物结构**

交付物是机器可解析的声明，人类可读视图由它渲染生成，不得反向修改；事实以 Supervisor 的核验与数据库记录为准：

```json
{
  "schema_version": 1,
  "task_id": "T-2",
  "attempt": 2,
  "session_id": "…",
  "status": "COMPLETED",
  "deliverable_kind": "code_change",
  "summary": "不超过 400 字符",
  "files_changed": ["src/uart.c"],
  "commands": [{ "argv": ["cargo", "test", "--frozen", "-p", "uart"], "exit_code": 0 }],
  "requested_dependencies": [],
  "assumptions_used": ["A-1", "A-2"],
  "contract_friction": [],
  "irreversible_actions": [],
  "questions": [],
  "leftovers": []
}
```

各字段的设计意图：

- schema 同时检查跨字段一致性：`COMPLETED` 不得包含未解决契约摩擦、依赖申请、阻塞问题或待授权动作；这些情况应为 `BLOCKED` / `NEEDS_CLARIFICATION`。阻塞时的字段形式为 `contract_friction: [{entry, why_impossible}]` 与 `questions: [{id, text, options, proposed_default, blocks}]`。
- `commands[].exit_code` 不采信模型自述。`argv` 只是复核请求，Supervisor 按任务允许的验证命令选择执行；禁止直接执行模型提供的任意 shell 文本，也不能用其命令替代项目配置的必跑验证。
- 每条验证命令有强制超时、关闭的 stdin（Unix `/dev/null`、Windows 等效空输入）与独立进程容器。超时、正常退出或失败后均清理全部子孙进程，确认结束后才生成可用于验收的收据、释放资源；清理失败也必须记录失败事实。默认拒绝 watch/服务类命令；确需服务的测试由显式 fixture 管理启动、就绪与回收。
- 验证在可重建的候选工作区内执行，产物写入独立构建目录；外部状态使用清理钩子或可复位夹具。关闭 stdin 与超时不等于幂等，无法复位或涉及不可逆副作用的命令按 INV-9 处理。
- `requested_dependencies` 是待办理申请，非空时以 `BLOCKED` 结束本次调用；Supervisor 退出后准备依赖快照，再启动下一 Attempt。已满足的依赖只记录在环境摘要中，不反复申请；申请不计模型失败，但调用数和耗时仍计总预算（§3.5）。
- `assumptions_used` 与注入清单交叉校验：声称使用了未注入的条目，说明上下文组装有缺陷或模型在幻觉，两种情况都值得记录。
- 交付物**不包含权威读集**。规范注入、源码访问与构建输入由 Supervisor 记录（INV-5），模型可以申请额外输入，但其自述不能证明依赖完整。
- `contract_friction` 触发契约评估；只有 Supervisor 接受规范变更后才按新旧版本计算级联，模型声明本身不修改依赖图。
- `questions` 必须结构化并一次性列全：一次 headless 调用只应消耗一次反问机会，逐条追问会使流水线停滞。
- 模型天然倾向于“直接动手”而非提问，因此账本中已有默认值的疑问应当自答，只有确实需要人决策时才升级，并批量提出。

### 3.3 状态层：冷热分离与单一写者

`.orgy/` 区分人类工作副本、AI 提案、运行态与交付出口（对应 INV-1、INV-3、INV-4）：

```text
.orgy/
├── spec/                          # [进 Git] 人类直接编辑的规范工作副本
│   ├── CONTRACT.md
│   ├── ASSUMPTIONS.md
│   ├── tasks/T-2.yaml
│   └── verification.yaml
├── drafts/<proposal>/             # [忽略] AI 提案与差异，等待人类采纳
├── runtime/                       # [忽略] 仅 Supervisor 写
│   ├── state.db                   # SQLite 权威状态；WAL/-shm 为伴随文件
│   ├── audit.jsonl                # 数据库事件的可再生文本导出
│   ├── logs/T-2.a2.jsonl           # 原始工具输出与验证日志
│   ├── recoveries/                # 终止后采集资料
│   └── supervisor.lock            # 本机排他锁的诊断信息
└── outbox/                        # 仅在 Worker 工作区存在
    └── T-2.a2.handoff.json
```

**人类编辑与显式发布**

人类直接在 IDE 编辑 `spec/`，保存后运行 `orgy apply` 或在 TUI 确认发布。删除后台文件监视与自动导入，不自动覆盖人类文件。Supervisor 始终从已发布的 `refs/orgy/specs/<rev>` 读取不可变规范；未 apply 的文件修改不影响在途任务。

`orgy apply` 在本机唯一写者中串行处理，步骤为：捕获指定文件集合与字节 → 校验 schema/引用及展示语义与说明差异 → 写 Git 对象并固定新规范 ref → 用数据库事务更新当前规范版本与事件。使用独立 Git 索引，不提交无关源码，也不修改用户索引或工作副本。AI 的 `spec_proposal` 写入 `drafts/`，用户审阅并把接受的修改放入 `spec/`，再走相同的 apply 流程。

显式 apply 减少竞态，但不能阻止用户恰在捕获时继续保存：捕获前后比对文件集合及内容摘要，变化则提示重新 apply；仅发布本次捕获并验证的字节。多文件变更由用户保存完成后一次发布，不以“语法合法”推断需求已编辑完毕。提交后的继续编辑属于下一版本，不后台吸收。

**SQLite 作为运行态事实源（INV-4）**

`runtime/state.db` 使用本地文件系统，初始化并核验：

```sql
PRAGMA journal_mode=WAL;
PRAGMA synchronous=FULL;
PRAGMA foreign_keys=ON;
```

连接级配置（尤其外键）在每个连接上设置。唯一 Supervisor 串行写入；查看界面可通过只读连接或 CLI 查询。按仓库身份/common Git dir 持有本机 OS 排他锁，其他命令连接该实例；未运行时命令取得同一锁后执行短期写者。PID 只供诊断，不作为锁。

- Task/Attempt 生命周期、规范版本、预算、资源占用、验证收据、待决外部操作与事件在同一数据库事务中更新；事务提交后才发布调度变化。用外键和唯一约束避免重复活动 Attempt、悬空记录和重复操作 ID。
- `audit.jsonl` 是带 `event_id` 的事后导出，可延迟、丢尾或重建；状态恢复只读数据库，绝不反放文本日志。不再维护自研哈希链、`state.json`、多代际检查点或日志裁剪协议。
- SQLite 管理自身 WAL 恢复与 checkpoint；磁盘满、I/O 错误或数据库损坏时停止派发并保留现场，不创建空数据库继续跑。数据库只能通过 SQLite 备份 API 或停机后一致备份复制，不能运行中仅复制 `state.db` 而漏掉 WAL。
- 外键不保护磁盘文件或 Git 对象。活跃候选/快照用受管 refs 保留；文件日志先写完再登记。首版只在无活动任务和待决操作时显式清理已结束任务资料，不实现引用计数 GC。恢复时核对被引用对象是否存在；数据库备份与 Git 仓库、恢复资料配套保留。

**数据库事务不覆盖 Git、进程与设备**

外部动作继续使用小型 `operations` 记录：`operation_id + intent(expected, target) → execute → outcome`。先提交意图，再执行，再提交结果；不跨长时间进程调用持有数据库写事务。SQLite 无法让这些动作与数据库原子提交：

- 规范发布先保存并固定 Git 对象，再提交当前版本指针；崩溃留下的未接受 ref 不参与调度。
- 代码晋升记录接受 ref、预期旧提交、目标提交、计划及收据；使用 Git CAS。恢复时 ref 已为目标则补记结果，仍为预期旧值且输入有效才可继续，其余情况停下对账。
- 进程记录执行 ID，恢复先回收旧实例再允许新 Attempt。烧录等不可逆动作结果未知时记 `UNKNOWN`，用户核对后再处理，不自动重放。

启动先取本机锁、打开数据库并核对未决操作，再接受新的 apply 或晋升。执行生命周期存数据库；`FRESH/STALE/DIRTY` 仅是收据派生的新鲜度，不能用它代表“进程是否运行”。

**输入变更与终止后采集**

派发记录规范语义哈希、上下文来源、代码基线与环境。只有受影响约束/目标/验收计划变更或权限收窄才抢占；说明性编辑不杀 Worker，纯代码漂移保存候选后重验（§3.6.4—§3.6.6）。

终止不要求 CLI 输出 `PREEMPTED` 总结。Supervisor 记录原因、停止整棵进程树并确认退出，再采集相对 `parent_tree_commit` 的代码差异、暂存/未暂存与合规未跟踪文件、日志尾部和恢复快照。日志只是线索；快照未保全或进程未回收时不 reset、不复用现场。下一 Attempt 接收最新约束与恢复摘要。

规范版本和代码接受版本分开：apply 不自动将旧代码判为满足新要求。仅说明文字变化时保留旧收据的适用性，不新建代码候选；语义变化必须重新验收。候选晋升时绑定实际使用的规范版本，不能覆盖主工作区中尚未 apply 的人类编辑。

### 3.4 本地执行环境与验证边界

**只实现当前宿主机需要的能力**

先支持用户当前的 Windows 本地环境，再按实际需要增加其他平台适配器。复用 CLI 原生权限、OS 进程管理与现有防火墙/容器能力，不自研跨平台挂载、下载网关或系统调用审计。工作目录参数不是权限边界；数据库、主工作区和 Git 元数据不授予 Worker 写权限。

Task 的 CWD、会话目录保持稳定；每次 Attempt 有独立临时区和 outbox，构建输出按 Task/候选分开。按工具实际支持的配置项设置路径；Windows 的 `TEMP`、`APPDATA` 等不与 `HOME` 混为一谈。只读角色仍需要这些私有可写目录。

| 角色/进程 | 项目输入与输出 | 网络 |
| --- | --- | --- |
| 架构/审查 CLI | 读取冻结规范与代码，输出提案/裁决到 outbox | 保留用户配置的模型连接 |
| 构建/测试 Worker | 声明写集、私有临时/构建区；包管理使用离线策略 | 模型连接保留；子工具能否独立断网按能力记录 |
| 依赖准备 helper | 修改任务私有依赖清单/锁与包缓存，不写控制面 | 仅该阶段为下载依赖联网 |
| 独立验证 helper | 干净候选副本、受保护验收计划、独立构建目录 | 默认 OS/工具沙箱断网；网络测试显式声明本地 fixture |

**预取依赖，离线构建**

依赖按 §3.5 准备完再启动需要它的 Worker。Supervisor 使用包管理器现有能力解析、锁定并预取；Cargo 可用 `cargo fetch --locked`，npm 可在临时依赖工作区用 `npm ci --ignore-scripts` 预热已锁定内容。具体命令由生态适配器选择，不能假定 npm 有通用 `npm fetch`，也不能把只禁止改锁文件的参数当作离线开关。

构建使用 `cargo test --frozen`（锁定且离线）或对应工具的已验证离线选项；`CARGO_NET_OFFLINE=true` 可用于所有 Cargo 子命令，但仍需锁定版本。npm 可使用支持版本上的 `npm ci --offline --ignore-scripts`；必要的生命周期脚本由计划单独授权在离线环境执行。缓存缺包时报告 `DEPENDENCY_CACHE_MISS`，回到 helper 预取，不悄悄联网或反复调用模型。

- 包缓存使用包管理器的普通目录和原生锁，可复用用户缓存或配置项目专属缓存。**离线不等于只读**：仍可能创建锁、解包或写元数据；不共享可写编译输出，也不把整个凭证目录暴露为缓存。
- 某生态不能安全并发访问缓存时，由本地调度器串行化相关命令，或普通复制缓存到 Task 私有目录。不实现下载服务、只读原子发布、OverlayFS 或跨平台 CoW；首版不启用共享编译缓存。
- 离线参数只约束包管理器，不约束 `build.rs`、安装脚本或任意子进程。独立验收仍通过现有沙箱/防火墙断网；无法做到时记录实际能力，不声称已完成隔离或可复现的离线验收。

**模型连接与凭证**

模型 CLI 仍需联网，不能把整棵 Worker 进程树断网。支持独立子工具策略时限制其网络；不支持时记录 CLI 与子工具共享网络/凭证信任域，Worker 自检只是辅助，正式验收始终由独立 helper 执行。删除内置 HTTP/SOCKS 代理和包仓库域名白名单模块；有需要时使用用户已有网络配置。

启动环境按用途筛选。模型凭证不复制到项目，验证/依赖 helper 不继承模型 Key、SSH agent 或推送凭证；私有包仓库凭证仅授予下载 helper。Supervisor 不直接运行仓库脚本：构建、安装和转换程序放在受限 helper 内，Git 管理操作禁用非批准 hooks、外部过滤器等隐式执行入口。

**本机进程回收与资源**

Windows 使用不可继承控制句柄、kill-on-close Job，优先创建时原子入组；没有该能力时必须覆盖已创建未入组窗口。其他平台复用现有服务管理器或本地回收机制，不为未来平台预建统一守护服务。超时与退出都清理全部子孙进程；重启确认旧进程结束后才复用路径或设备。无法确认时保留现场并提示用户处理，不把 PID 文件或超时当作资源已释放。

启动探针检查实际采用的工具参数、交付/续接能力、目录授权、网络和回收能力；只实现需要的探针，不引入通用权限策略语言。缺少某项优化条件则关掉优化；缺少任务必需的权限或回收能力则不运行该任务。

**验收计划与候选副本**

用户通过 apply 发布 `spec/verification.yaml`，固定必跑检查、工具/计划版本、超时、资源与跳过规则。候选新增测试可作为补充，不能删除/放宽基线检查来获得通过；零用例或非允许跳过按失败处理。

默认 `verification_isolation: local_checked`：从精确候选提交复制/检出独立验证目录，使用独立构建目录和固定 runner；验证前后计算真实文件清单（路径、类型、内容、删除与新增），结束并清理进程树后再对账。有遗留输入变化就拒绝收据；需要生成受跟踪源码时先形成新候选，再验证。仅检查 HEAD tree 或 `git status` 不足以覆盖未跟踪/被忽略输入。

此模式不要求源码只读挂载，适合可信本地脚本；它只能检测**最终留下的变化**，不能发现“修改源码 → 测试 → 恢复”的临时篡改。需要防范这种行为时，可选现成只读权限/容器能力的 `protected` 模式，并实测写入会被拒绝；没有能力则不能提供该保证。普通只读文件属性也不构成同权限恶意代码的安全边界。收据记录模式及其信任前提，不能互换为更强等级的证明。

正式验收从空构建目录开始；Task 的增量缓存可用于自检，不能代替验收。每个新集成候选都执行完整验收；默认不为省一次构建引入额外缓存服务。

### 3.5 工作区隔离与两阶段验证

**Task 工作区与 Attempt 快照**

每个 Task 使用固定路径 `/worktrees/<task>`，本地占用记录覆盖多次 Attempt，同一 Task 不得并发执行两个 Attempt。Supervisor 管理 Git 元数据与提交；采用 detached HEAD 或专属 Task 分支，避免将同一分支同时检出到多个 worktree。Worker 不得改动共享 refs、hooks 或其他任务元数据。

文中“主干/main”指受管接受 ref，默认使用 `refs/orgy/accepted`，从用户选定提交初始化；不直接移动用户正在检出的分支。向用户分支集成或向远端发布是明确的后续操作。这样接受候选不会使人类工作区的 HEAD、索引和文件脱节。

每个 Attempt 在启动前记录 `spec_revision`、`parent_tree_commit`、`attempt_start_commit`、`upstream_candidates` 与 `dependency_snapshot_id`。`parent_tree_commit` 是**本任务累计增量的对账基线**：普通任务从接受基线构造，组内下游从指定上游候选的合成树构造，再计入 Supervisor 准备的依赖/规范差异。它不一定等于主干，也不一定等于续接前已含本任务部分修改的 `attempt_start_commit`。

结束后确认进程树静止，保存完整现场，再以 `git diff <parent_tree_commit> <attempt_snapshot>` 对账本任务累计的 `files_changed` 与写集。合法暂存/未暂存修改、删除、未跟踪文件进入不可变快照 `refs/orgy/attempts/<task>/<n>`；缓存、凭证、outbox 不入代码提交，越界内容另存证据。Supervisor 生成的依赖差异独立记录、不算 Worker 写入；不能靠过滤掉越界 diff 来掩盖违规。该 ref 只表示恢复点，不表示验收通过。

`restart` 保留现场并按 §2.1 续接；`reset` 在快照成功后才还原到选定基线，显式处理未跟踪文件。`git reset --hard` 不会清理未跟踪文件，不能代表完整恢复。续接保留累计增量的父基线；换基线则在新实例中重新记录父树、来源与输入，不改写旧记录。回收只针对无活进程、无占用且恢复资料已保全的目录。

**写集与物理资源**

调度器检查 `writes.public ∪ writes.private` 的路径交集；worktree 只是实现隔离的手段，不保证语义兼容。默认串行，只在契约接缝处并行。路径规范化须考虑大小写、符号链接与通配符，不能确定不相交时保守串行。

`resources` 声明本机独占资源，如 `hw:board-1`、`hw:stlink-1`、`port:8080`。简单配置表将串口、稳定设备名与同板 JTAG 归为同一板卡；唯一 Supervisor 一次取得所需占用，退出、清理与必要复位完成后释放。局部验证接管原占用或先释放再获取，避免自己等自己的锁；排队/等待用户时不占设备。

删除跨主机租约服务与 fencing token。用户手工调试前在本地暂停/释放相应设备；检测外部占用时提示处理，不保证协调任意外部程序。即使用 SSH/串口转发访问设备，也只是本机独占配置的端点；断连后状态未知须核对，不把它扩展为远程调度系统。

**共享构建配置单写者**

默认禁止 Worker 修改共享构建清单及锁文件；采用**先申请、后准备、再续接**的简单流程，不建设运行中双向控制通道：

1. 已知依赖在派发前准备。运行中发现缺少新库时，Worker 保存现有代码，以 `BLOCKED` 携带 `requested_dependencies` 退出；可以报告真实的失败自检，但不能虚构已通过或声明 `COMPLETED`。
2. Supervisor 收集并对账现场，按用户预设的依赖规则或用户确认决定是否接受；拒绝则反馈原因，不默默换版本。helper 在普通临时目录更新清单、锁版本并联网预取，成功后保存不可变依赖快照。不实现挂载覆盖层；失败停留在依赖准备状态。
3. 旧进程退出后，Supervisor 将快照中的清单/锁放到 Task 工作区，记录自己的差异。以原父树为基础生成包含依赖配置的新父树，再三方应用原任务累计代码增量，避免把此前 Worker 修改混入新父树而漏掉对账。
4. 启动下一 Attempt，注入依赖版本与准备结果，按支持能力续接；Worker 离线自检通过后才声明完成。环境变化会使旧局部收据失效；已满足请求不再重复办理。

依赖阻塞不计模型失败次数，但两次调用、helper 耗时与重复申请都计入总预算。申请内容以生态、manifest、name、版本约束、features 和来源规范化，结合当前依赖快照判断是否已满足；同一未变请求不会无限触发下载/重启。

例如缺少 serde 的 Attempt 返回 `status: BLOCKED`、`commands: []`、`requested_dependencies: [{ecosystem: cargo, manifest: Cargo.toml, name: serde, version: "1", features: [derive]}]`。准备成功后下一 Attempt 才运行 `cargo test --frozen`，最终交付的 `requested_dependencies` 为空。

集成时由 Supervisor 合成各成员的依赖请求，检查约束冲突并生成最终清单/锁，再预取并完整验收；依赖解析变化必须重验。`cargo add` / `npm install` 不天然确定，解析器与锁摘要进入环境记录。其他构建配置也提交提案，由专门串行任务在最新基线上处理。暂不采用让 Worker 任意改 manifest 再反解析的方案，避免丢失脚本、workspace、target 条件等非依赖语义。

**两阶段验证与串行合并队列**

1. **局部检查与对账**：Worker 自检后，Supervisor 对比 `files_changed`、实际差异与写集，复核预定的局部命令；依赖覆盖的生成差异单独对账。对账覆盖删除、模式变化及未跟踪/被忽略的受管文件，不能让 `.gitignore` 隐藏产物。对账及适用局部检查通过可发布冻结候选，不代表完整验收或合入。
2. **队列排序**：以集成单元为粒度，先满足依赖拓扑，再按就绪完成顺序排队。以已接受代码 `S0` 为基线，为单元 `U1` 构造 `S1 = S0 + U1 + Supervisor 配置/规范变更`，在隔离 staging 上按目标规范运行完整验收计划。若旧 `S0` 尚未满足新规范，记录其旧通过版本和已知失败，不能将迁移所需失败误判为环境异常。
3. **按已验证提交晋升**：完整验收及所需审查通过后，在同一提交临界区重查目标规范/计划、权限与资源条件，并对接受 ref 执行预期旧值为 `S0` 的 CAS；仅晋升精确 `S1`。基线或约束变化则重建/重验；任何审查后修改使旧收据失效。晋升意图与结果按 §3.3 对账恢复。
4. **串行验证**：一次只验证并晋升一个集成单元；Worker 开发仍可并行。删除投机预验队列，避免维护失败前驱后的成批重建与收据作废逻辑。
5. **失败定位与路由**：失败先隔离当前集成单元，发送差异与日志给其责任任务；此前已接受单元不被连坐打回。队列定位的是失败增量，不证明某任务单独有错。复跑同规范/同环境的已知通过基线、最小组合复现或有限二分可辅助归因；新规范下从未通过的基线不能充当回归证据。诊断重跑有预算，不能无限重跑直到通过。

所有候选均执行完整验证，不允许 `public_digest` 截断该阶段。验证命令的超时、无交互、进程回收与副作用规则见 §3.2。

**跨任务接口迁移的原子集成**

单任务无法独立通过新规范时，优先改为一个垂直切片；确需多个 Worker 时，在任务定义中声明共同的 `integration_group`，同时固定组成员、目标规范、内部依赖与预算。例如驱动接口变更与解析器迁移组成一组，避免“驱动等旧解析器测试通过，解析器又等驱动先接受”的环形等待。

组内按无环依赖消费上游不可变候选，绑定 ID、摘要与 `parent_tree_commit`；组外只消费已接受结果。组内仍遵守写集/资源互斥，完整验收针对单个合成候选执行，整组 CAS 晋升。组大小/耗时有上限；规范切换所需消费者必须纳入组或采用兼容迁移，不能靠跳过检查推进。

例：`C_A = S0 + ΔA`，B 的父树为 `C_A`，快照为 `C_B = C_A + ΔB`。B 的写集与 `files_changed` 只对账 `diff(C_A, C_B)`，不能对账 `diff(S0, C_B)`；组装时仅提取各任务自己的增量，不能把继承的 `ΔA` 再算一遍。多个上游先合成一棵无冲突父树并固定提交，再启动下游。

A 更新为 `C_A'` 时，B 的旧验证证据失效，代码快照仍可复用。旧 B 进程先结束或被回收；Supervisor 在临时集成目录以 `base=C_A, ours=C_B, theirs=C_A'` 三方应用 B 的累计增量，生成 `C_B'`，再次检查 `diff(C_A', C_B')` 仍在 B 写集内并重验。成功就更新候选和父树来源，不调用模型；冲突、越界或重验失败才启动 B 的修复 Attempt。旧 refs/生成清单保留，不对活动工作区或已记录提交直接 rebase；目标规范变化仍按规范失效处理，不能靠文本合并绕过。

验收计划预先区分 `member-local` 与 `group-only` 检查：依赖尚未迁移消费者的全项目编译属于后者，组员完成对账及可独立检查后即可发布组内候选，将组级检查标为 pending。若不存在可独立的语义检查，至少完成协议/范围对账，但不得声称已验证功能。整组所有必跑检查通过才接受，不能运行失败后临时把检查改为延期。

**防止规范层回流与副作用**

Worker 的 `.orgy/spec` 为冻结的可读快照；Supervisor 只应用代码增量，不合并 Worker 的规范修改。候选规范与其记录的 `spec_revision` 字节一致，否则记 `SPEC_LEAK`；晋升时与当前发布的语义约束对账，语义改变须重验，纯说明变更不强制重建候选。若原稿是验证输入则仍按字节失效。正常规范迁移允许 Supervisor 物化受控差异，不回写人类工作副本，也不依赖本地 Git 合并驱动。

硬件、推送与外部写入由 Supervisor 的本地授权命令入口执行，不建设独立 broker 服务。Worker 默认没有原始设备/远端写权限；请求包含 `action_id`、稳定目标、参数与产物摘要，用户按动作或已批准范围放行。执行前核对本地占用并提交数据库意图，结束记录结果；结果未知挂起核对，不自动重试。

串口/JTAG 的原始句柄通常无法区分“查询”和“烧录”；无法细分的工具按整条命令最高副作用能力在执行前授权，由本地 helper 持有设备。`irreversible_actions` 只是申请，漏报也不能获得句柄。已经开始的不可逆操作不会因普通 Worker 抢占而自动重启；安全停止无法确认时进入未知态，提示用户核对后再释放资源。

### 3.6 语义化规范层与增量重算

#### 3.6.1 动机

如果规范只以散文存在，就无法回答两个必须回答的问题：

1. 修改了某个接口，哪些任务受影响？
2. 人类修改了某条假设，哪些产出需要重算？

回答不了，级联重置就退化为全量重启，增量收益为零。因此规范层必须同时满足两个看似冲突的要求：**人类可读、可自由组织**，以及**机器可解析、可精确求差**。

解决方案是“文学化结构化规范”（literate structured spec）：散文照常书写，所有具备约束力的内容封装在带语言标签的围栏代码块中，并赋予全局唯一、不可复用的稳定 ID。

#### 3.6.2 条目格式

假设条目（`spec/ASSUMPTIONS.md`）：

````markdown
### 硬件通信层

雷达模块经开发板 UART2 接入，初期未启用 DMA，采用轮询读取：

```yaml assumption
id: A-1
topic: 雷达串口波特率
value_type: integer
value: 115200
status: active
rationale: 该波特率与雷达模组出厂固件一致
```
````

契约条目（`spec/CONTRACT.md`）：

```yaml contract
id: IF-3
kind: interface
depends_on: [A-1, A-2]
sig: "int uart_read(uint8_t *buf, size_t len)"
invariants:
  - 成功时返回读取字节数，硬件错误返回负值
  - 非阻塞，必须在 1ms 内返回
```

任务条目（`spec/tasks/T-4.yaml`）：

```yaml task
id: T-4
title: 实现雷达字节流解析器
objective: 将字节流解析成完整雷达帧，拒绝长度错误和校验失败的帧
role: core_builder
deliverable_kind: code_change
change_policy: optional
acceptance: [parser.valid_frame, parser.invalid_frame, regression.required]
verification_plan: parser-v1
integration_group: null
inputs:
  contracts: [IF-3, IF-4]
  assumptions: [A-2]
  tasks:
    - id: T-2
      mode: public
      paths: [include/uart.h]
  source_paths: [src/parser.c, include/parser.h]
writes:
  public: [include/parser.h]
  private: [src/parser.c]
resources: []
implements:
  - contract: IF-4
    target: host
    implementation: parser.default
```

上述条目是格式片段，省略的 `A-2`、`IF-4`、`T-2` 及验收计划须在实际规范中存在。`objective` 与 `acceptance` 是验收约束；`title` 仅供界面展示。验证计划由受保护配置定义，包含必跑命令及成功判据，不能只凭“实现了某接口”推导完成。

`inputs.tasks[].mode` 可为 `public` 或 `full`，缺省按 `full`；`public` 只为满足 §3.6.4 文件集边界的局部检查选择上游公开产物，不限制或证明 Worker 的全部认知依赖。`paths` 选择相应输入，`source_paths` 声明自身或其他源码。`writes.public/private` 都计入写互斥；公开文件中的 inline、宏、模板仍按字节计入摘要。

硬件任务可声明 `resources: [hw:board-1, hw:stlink-1, port:8080]`；资源别名与整板独占关系由注册表解析（§3.5）。

**一个代码块只放一条条目**，便于 ID 定位、差异与提案合并，但不保证 Git 永不冲突。条目增多后按主题拆分文件；人类直接编辑并 apply，AI 提案按 ID 展示差异，不引入自定义 Markdown 合并驱动。

**ID 与命名空间**：`A-*` 表示假设，`IF-*` 表示接口，`T-*` 表示任务，`INV-*` 表示本文档中的不变量。条目 ID **不可复用**：删除条目时保留块并标记 `status: retired`，禁止删块后把同一 ID 分配给新条目。否则历史交付物中的读集哈希可能“恰好”匹配到一个无关的新条目，产生假阴性。

#### 3.6.3 语义投影与有效哈希

**第一步：语义投影。** 对条目文本直接取哈希是错误做法，因为块内的排版调整、说明性字段修改都会触发级联。正确的做法是每种条目声明一份**语义投影白名单**，只对具备约束力的字段取哈希：

```yaml
# 工具配置中的投影定义
assumption:
  semantic: [id, topic, value_type, value]
  ignore:   [rationale, note, owner, last_verified, status]
  # status 仅 active/confirmed 互转时忽略；进入 retired 按删除处理（§3.6.6）
contract:
  semantic: [id, kind, sig, invariants]
  ordered:  { invariants: false }
task:
  semantic: [id, objective, role, deliverable_kind, change_policy, acceptance, verification_plan, integration_group, writes, resources, implements]
  ignore:   [title, notes]
```

`depends_on`、`inputs` 的依赖描述单独规范化并参与有效哈希，包含目标 ID、边类型、`mode` 与路径选择，不能只哈希目标内容而遗漏边的含义。规范依赖与代码产物依赖分开求值，后者另进入任务输入摘要。

`verification_plan` 解析为已发布验收计划的语义内容哈希；组成员 ID、内部边与目标规范的语义声明进入组摘要，不把纯说明修订号或成员有效哈希再滚回声明，避免说明改动失效和哈希环。集成候选另外绑定成员定义与产物摘要。任务自身及控制依赖不能由 Worker 的 `inputs` 省略。预算/模型配置记录版本，但纯成本参数不作为代码行为变化。

三条要点：

- **`status` 的语义需要拆分**。`active ↔ confirmed` 只是元信息，人类“确认某条假设”不应触发任何重算，因此不进入语义投影。但 `→ retired` 是语义终止事件，必须按删除处理（§3.6.6），否则会出现“假设已作废但没有任何产物被重算”的静默过期。
- **集合与有序序列必须显式区分**。`invariants` 是集合，排序后再哈希；但硬件场景中 UART 寄存器初始化序列的**顺序本身是语义**，此类字段需要 `ordered: true`。不区分会得到“顺序改了但哈希没变”的错误结果，比多算一次更糟。
- **按 schema 归一化**。默认保留标量类型，整数 `115200` 与字符串 `"115200"` 不等价；`value_type: integer` 下拒绝字符串，只有显式转换规则才可转换。注释和合法空白可忽略。版本号、标识符、浮点值与有序字节不得用通用字符串/数字转换抹平；拒绝重复 YAML 键及不受支持的隐式类型。

**第二步：有效哈希（Merkle 滚动）。** 仅靠内容哈希无法表达“接口内容没变、但它依赖的假设变了”这种间接影响。与其为此增设“间接受影响”之类的中间状态，不如把依赖关系滚进哈希本身：

```text
content(e)   = H( schema_version, projection_version, normalization_version,
                  kind, id, projection(e) )
effective(e) = H( id, content(e), normalized_dependency_descriptors(e),
                  sort[ (id(d), effective(d)) for d in spec_deps(e) ] )
```

其中 `H` 为哈希函数（如 SHA-256），编码使用无歧义的规范序列化。`projection(e)` 是条目的语义投影，`spec_deps(e)` 包含显式规范依赖与上述验收/组控制依赖。依赖集合先排序，书写顺序不影响结果；schema、投影或规范化规则变化使对应旧摘要失效。

这样做的直接收益是**失效判定只剩一条规则**：

> 规范读集内条目的有效哈希变化即使该输入失效；全部规范哈希未变仅说明规范输入未失效。

规范变化沿规范依赖链滚动；源码、工具链与运行环境是否失效仍需独立检查（§3.6.5）。

调度图区分规范边、控制依赖与产物边。`inputs.tasks` 是**产物边**：组外等待上游接受，组内按 §3.5 消费冻结候选并绑定父树。仅满足文件集条件的局部检查使用 `public_digest`，其余按完整代码/产物输入处理。下游的规范边独立失效，不能被相同产物摘要截断。

#### 3.6.4 规范上下文与检查输入

**规范原稿可读，语义与解释分开**

默认 worktree 中保留对应已发布版本的 `.orgy/spec/`，Worker 可读原稿及 `rationale/notes`，也会收到相关条目的结构化注入。原因说明能帮助模型理解约束；不再承诺“只给语义字段”却同时暴露整个 Git 原稿。

记录两种摘要，目的不同：

- `requirements_digest`：实际可读规范条目的语义有效哈希，加任务目标、验收计划等控制依赖。默认整份规范可读时记录所有可读条目的语义，不能只记录提示词提到的 ID。
- `context_digest`：原稿字节、说明文本与会话来源，保存在 `generation_manifest` 中说明模型当时看到了什么。它不是已通过代码验收的自动失效键；更换说明可能影响将来的模型输出，不代表旧产物自动不满足原有要求。

仅说明变化时更新来源版本，不抢占任务、不重新调用模型、不自动推翻旧验收；真正需求必须写入条目。关键词检查不能证明散文没有新约束，apply 显示“仅说明变更”让用户核对；意图改变时修改结构化字段，或显式要求重新评估。说明文字与约束冲突时 Worker 应提问而不是把文字默认为新要求。

这是一项明确的规范治理规则，不是对自然语言语义的自动证明。若构建器、生成器或测试把规范原稿当作实际输入，例如读取 Markdown 生成代码或校验文档，则那些文件的**完整字节**进入相应检查输入摘要，修改标点也可能使该检查失效。源码快照只有在这种角色区分成立时才可排除作为纯说明的 `spec/`；不能无条件忽略所有 Markdown。角色提示、项目指令与工具配置仍按约束性输入处理。

**源码只保留两种处理方式**

1. **默认全量检查**：记录冻结源码、依赖锁与工具链；代码输入变化后重新验证。Worker 可读项目全量代码，不假设声明的 `mode: public` 就证明其没有读实现。首版禁用接口级复用，保留完整集成验收。
2. **可选文件集检查**：只为特定局部检查复制自身源码、声明头文件/接口包及构建描述到临时目录，使用明确工具链/标准库和已锁定依赖。记录整份清单、命令、环境和工具链摘要；相同文件集可复用该项检查结果。默认复制而不硬链接，防止写共享 inode 改动原件。

文件集编译成功只证明**该次检查**在记录的输入环境下通过，不证明模型生成代码时没有其他依赖。临时目录本身也不隔离绝对路径、符号链接、`CPATH`、旧缓存或外部包；清理搜索路径和缓存，拒绝指向原仓库的链接，使用现有沙箱约束项目读取范围。若不能排除这些输入，就按全量方式重跑，不能开 `public` 截断。无需为这一优化实现系统调用、mmap 或 ENOENT 跟踪。

源码路径可见性、标准库和包依赖仍是显式环境条件；不通过字面量扫描推断完整实际读集。局部文件集证明不授予整个 Task/Session 仅接口依赖资格，也不用于跳过集成、运行时或硬件验证。

**生成来源与迁移证据**

`generation_manifest` 保存 `parent_tree_commit`、`attempt_start_commit`、上游候选、规范/上下文与依赖快照；`validation_manifest` 描述当前候选重验时的真实输入。自身文件修改前像仅用于来源与三方应用，最终文件归 `code_digest`，不因自己的修改而自失效。

同一路径的外部修改按 base/ours/theirs 合并，不能冒充自身修改。迁移后生成新的候选和验证记录，保留原始来源；验证通过不等于模型曾看过新基线。Session 续接注入基线/依赖变化说明，语义约束已变或会话污染则 reset。

#### 3.6.5 验证收据与派生状态

新鲜度由数据库中的验证收据派生，不作为可独立编辑的事实；可缓存派生视图，但须关联数据库事件 ID 并能重算。执行生命周期由 §3.3 的事务状态维护，不能用 `FRESH` 表达“当前是否有进程运行”。

```yaml
receipt:
  task: T-4
  execution_id: T-4.a2.verify1
  scope: local             # local / integration；两种收据不能相互替代
  spec_revision: sha256:…
  requirements_digest: sha256:…
  parent_tree_commit: "…"
  dependency_snapshot_id: "…"
  verification_isolation: local_checked
  task_definition_digest: sha256:…
  generation_manifest_id: T-4.a2
  inputs_digest: sha256:…   # validation_manifest：实际检查输入，不混同辅助上下文
  code_digest:   sha256:…   # local 为任务产物；integration 为完整候选树
  env_digest:    sha256:…   # 工具链、命令、策略、锁文件及资源/fixture 配置
  verification_plan_digest: sha256:…
  candidate_commit: "…"   # 集成收据必须绑定精确候选提交
  argv: [cargo, test, --frozen, -p, parser]
  exit_code: 0
  required_checks: [parser.valid_frame, parser.invalid_frame]
  results: {parser.valid_frame: passed, parser.invalid_frame: passed}
  cleanup: confirmed
  log_ref: runtime/logs/T-4.a2.jsonl
```

新鲜度按收据**派生**，不另存可独立修改的事实：

| 派生状态 | 条件 |
| --- | --- |
| `FRESH` | 最新适用收据所有必跑检查通过、清理确认，且定义/计划/输入/代码/环境摘要与候选绑定均一致 |
| `STALE` | 旧收据曾通过，但任一摘要、作用域或候选绑定与当前不一致 |
| `DIRTY` | 无收据，或最近一次验证未通过 |

新鲜度按 `(任务定义, 检查作用域, 候选)` 分区，不能让旧候选迟到的失败污染新候选；同一分区内最近失败优先。仅对计划所要求的全部检查均满足时派生整体通过。结论只对记录的输入证据成立；硬件状态无法完全内容寻址时，每次重新初始化并验证，不跨运行复用硬件收据。工具链、命令、锁文件或隔离策略变化同样使旧收据失效。

`spec_revision` 与生成上下文仅供溯源；规范新鲜度比较 `requirements_digest`，不因纯说明修订号变化失效。候选提交本身变化仍须重新完整验收；仅修改说明并 apply 不移动代码接受 ref。原稿被验证程序实际消费时，其字节进入 `inputs_digest`。`local_checked` 的结果不能当作 `protected` 验证结果。

#### 3.6.6 级联重算流程

规范变化只有用户 apply 才生效：**捕获并校验工作副本 → 保存不可变 Git 快照 → 提交 SQLite 规范版本/事件事务 → 发布调度版本**。不回写人类文件。说明变化只更新上下文来源，以下流程针对语义变化；外部 Git 操作仍按 §3.3 对账。

1. 比较新旧有效哈希映射，得到变更条目集合（新增、修改、删除均视为变更）。
2. 沿规范边求有效哈希变化，并沿产物边建立潜在受影响闭包；潜在可达不等于立即重派全部任务。
3. 按拓扑序及以下优先级处理：
   - **规范/任务目标/验收计划失效或权限收窄**：正在运行的按 §3.3 终止并采集，携带新定义重派；同样的代码摘要不能覆盖控制依赖变化。
   - **仅源码、上游产物或普通工具链输入漂移**：旧收据失效，但允许活跃 Worker 在冻结基线上结束。保存候选，将其代码增量三方应用到最新已接受基线后重新完整验收；有冲突或验证失败才派发修复。禁止把每次无关主干提交都变成全体 Worker 重启。
   - **仅产物边潜在影响且摘要未变**：只在局部文件集检查的输入、环境与计划均不变时复用该项结果。组内父树变化按 §3.5 迁移自身增量并重新验证，不直接复用旧候选收据。
4. 接受新产物后按当前接受树发布 `artifact_digest` 与 `public_digest`。任何任务修改已有声明产物，都更新该路径相关产物索引与消费者，不能一直拿原生产任务的历史提交作当前摘要。按 §3.6.7 决定局部截断，完整集成验收始终执行。

队列有失败预算与公平性约束：单元受阻时只阻塞其依赖者；与其无依赖的就绪单元可在最新接受基线上继续排队。接口迁移使用显式集成组，不能让一个永远失败的队首阻塞全项目。

**示例**：`A-1` 的波特率由 115200 改为 921600。

| 节点 | 关系 | 处置 |
| --- | --- | --- |
| `A-1` | 变更源头 | 内容哈希改变，有效哈希改变 |
| `IF-3` | `depends_on: [A-1]` | 自身内容未变，有效哈希改变 |
| `T-2`（串口驱动） | 读集含 `A-1` | 直接命中：中断、重置、携带新值重新派发 |
| `T-3`（串口测试） | 读集含 `A-1`、`IF-3` | 直接命中：同上 |
| `T-4`（帧解析器） | 读集含 `IF-3`、`T-2` | 直接失效：`IF-3` 的有效哈希已变，不能被 `T-2` 的接口摘要截断 |
| `T-8`（极坐标渲染） | 规范视图仅含 `IF-7` 且不依赖 `A-1` | 无关；若默认可读全份规范，则保守纳入其可读语义集合 |

若只调整 `T-2` 内部实现，公开文件和规范语义未变，则 `artifact_digest` 改变、`public_digest` 不变。`T-4` 的某项文件集接口检查可在其全部输入不变时复用；这不免除实际实现的链接、行为测试或新候选完整验收。默认全量检查仍重跑。

**删除与引用完整性**

以下四类情况必须在**写入磁盘时**校验，而不是等到运行时才发现：

| 情况 | 后果 | 处置 |
| --- | --- | --- |
| 删除条目 | 引用者在遍历中找不到起点，静默漏算 | 删除即变更：所有引用者进入受影响闭包；悬空引用直接阻止派发 |
| ID 复用 | 旧读集与新条目哈希偶然匹配，产生假阴性 | 禁止复用，删除后保留 `retired` 标记与墓碑记录 |
| 依赖成环 | 遍历不终止，受影响范围等于全库 | 提交时环检测，拒绝落盘 |
| 实现身份冲突 | 同一目标下误创建重复实现，或将 mock 与生产实现混淆 | 按 `(contract, target, implementation)` 识别实现；允许历史/后继任务修改同一实现，并发仍受写集互斥约束 |

这四项检查的代价是与条目数量成正比的线性扫描，远低于事后排查的成本。

#### 3.6.7 早期截断

早期截断按**依赖边与验证作用域**决定，不以单个摘要推断行为等价。物理计算边界为：

```text
artifact_digest(T) = H(sorted_manifest(writes.public ∪ writes.private))
public_digest(T)   = H(sorted_manifest(writes.public))
```

`sorted_manifest` 对已接受快照中的规范化相对路径、文件类型/可执行位、文件字节内容摘要或链接目标做规范编码，包含声明模式与匹配集合，使新增、删除、重命名也改变摘要。声明范围内的必需生成产物须显式纳入，不以 mtime 或模型所称“等价”代替内容。跨边界符号链接必须拒绝或展开并纳入真实目标依赖。

基础版本只哈希文件，不承诺语言级 AST/ABI 等价分析。头文件、`.d.ts`、接口包中的注释变化也可能改变 `public_digest`；这会多算，但不漏算。C++ 模板、Rust 宏与其他携带实现的公开产物不享有“只有签名”的假设。

| 依赖/验证范围 | 摘要与截断规则 |
| --- | --- |
| 公开接口的局部文件集检查 | 比较 `public_digest` 及完整文件集、命令、环境；未变时只复用该项检查 |
| 读取实现或完整产物的依赖 | 比较 `artifact_digest` 及其他真实输入；实现改动使其失效，即使只是注释也保守重验 |
| 链接、运行时行为与硬件验证 | 纳入完整实现/二进制和环境，不能用 `public_digest` 截断 |
| staging 候选完整验证 | 每个候选重新执行；收据绑定完整候选与前驱，不因接口相同而跳过 |

检查发现外部路径/缓存泄漏、缺少环境摘要或存在独立规范变更时，禁用接口复用。`artifact_digest` 相同也要求其他检查输入不变。此优化只节省重复局部检查，不宣称证明模型仅依赖接口，也不节省新集成候选的完整验收。

#### 3.6.8 散文的咨询通道

说明文本默认辅助理解，原稿可读，但不自动改变正式要求；若原稿本身是构建/验证输入，则按字节处理（§3.6.4）。将说明与约束分离仍有两个产品风险：

- 人在散文里写下带约束力的话（例如“帧必须以 0xAA 开头”“不要再引入新的第三方依赖”），系统毫无反应，而人以为它已经生效；
- 散文修改反映的是**意图漂移**，而意图漂移恰恰是假设账本存在的理由。

因此散文进入**咨询通道**，而不是正确性通道：

1. 对规范性语气（“必须”“禁止”“shall”等）做提示，但不能据此证明没有隐含要求；“波特率现在是 921600”没有这些词也会改变意图。
2. apply 展示语义差异与说明差异；仅说明修改不自动重算。用户若改变需求，应修改对应条目或显式要求重新评估；AI 可生成提案，不能后台覆盖人类文件。

这样既保住了“零浪费”，也避免了“人以为的约束”与“系统实际的约束”之间的裂缝。

#### 3.6.9 未声明读的兜底

§3.6.4 的读取边界与保守回退是正确性前提；以下措施用于发现遗漏，不能替代它们：

1. **字面指纹扫描**。假设值发生变化时（如 `115200 → 921600`），在受影响范围之外全库检索该字面量；命中未声明依赖的文件则记 `UNDECLARED_READ` 告警。对常量类假设非常有效，代价接近于零。
2. **完整候选验证与周期性干净重验**。每次合并运行完整验证，周期性在无增量缓存的干净环境检查构建可复现性；硬件按 fixture 复位。依赖图可节省模型调用与有证据支持的局部重复验证，不能跳过候选集成验证。测试覆盖不等于依赖证明，全绿也不能证明隐藏源码依赖不存在。

#### 3.6.10 提交时校验清单

规范提交前必须通过以下检查，任一失败即拒绝写入：

| 检查项 | 目的 |
| --- | --- |
| 条目 schema 合法 | 保证可解析 |
| ID 唯一且未在墓碑列表中 | 防止 ID 复用 |
| 语义投影字段齐备 | 保证哈希可计算 |
| 引用完整（`depends_on`、`inputs`、`implements` 均可解析） | 防止悬空引用 |
| 无环 | 保证遍历终止 |
| 实现身份与构建目标合法 | 允许串行后继任务、不同目标实现与 mock，不使用全局任务引用唯一性 |
| `writes.public/private` 分类完整且不重叠，路径与上游产物选择合法 | 明确摘要与写隔离边界 |
| `resources` 可解析，资源别名归一，验证命令具备超时与清理策略 | 防止设备争用与孤儿进程 |
| `mode: public` 的检查有完整物化文件集与明确环境 | 无边界证据时按全量方式检查，不实现访问审计 |
| 任务目标、交付类型、变更策略及验收计划完整 | 防止改目标不失效、空 diff 误判和零检查通过 |
| 集成组成员、内部依赖、目标规范与预算合法 | 防止跨任务迁移死锁与无限合并批次 |

无引用接口、规模异常、可疑散文等是规划告警，不与 schema/引用损坏混作硬性拒绝；缺少优化能力时采用声明过的保守模式，缺少必要隔离能力时才拒绝派发。

## 4. 协同拓扑与闭环流转

### 4.1 角色分工

| 角色 | 定位 | 推荐模型 | 输入边界 | 核心职责与约束 |
| --- | --- | --- | --- | --- |
| **架构统筹** | 需求解析与调度 | 强/慢 | 原始需求、目录树、验证结果、契约摩擦报告、假设账本 | 按需唤醒。产出极简契约与切片任务；**只提交变更提案，不直接写盘** |
| **核心构建** | 业务与底层逻辑 | 快/廉价 | 单任务描述、读集条目、1~2 个直接关联源文件 | 遵循契约实现功能；探索期禁止防御性代码与过度抽象；契约不可行时提交 `contract_friction` |
| **测试与工具** | 验证与仿真 | 快/廉价 | 读集条目、运行环境与硬件规范 | 与核心构建并行。依据契约编写测试、Mock 与模拟器；新增测试作为补充，不能修改受保护的最低验收标准 |
| **对抗性审查** | 冗余与偏离检查 | 强/慢 | 差异集、读集条目、集成日志 | 条件触发（见下）。输出结构化裁决，不通过则附精简指令打回 |

**审查角色的触发条件与评价标准**

每轮都让强模型阅读全量差异会占据主要成本，且“是否过度设计”本身主观。改为条件触发：差异超过 N 行、出现新文件、新增依赖、跨任务边界、到达检查点。

评价标准必须可判定，例如：是否修改了写集之外的文件？是否引入只有单一调用者的新抽象？是否新增契约中不存在的依赖？差异规模与任务声明规模之比是否异常？输出结构化裁决而非散文评论。

**接口一致性由可执行检查验收**。类型、签名等可机械检查的契约绑定编译/接口检查器；“非阻塞、1ms 内返回”等行为约束须绑定具体测试、测量环境与阈值。自然语言不能自动变成完整的测试 oracle，模型生成的测试先作为候选证据，经认可后进入验收计划。暂不可自动检查的要求显式设置人工验收项，不宣称“机器全绿”已经覆盖它；模型审查可发现语义风险，但不替代这些验收项。

### 4.2 失败分类与升级阶梯

“失败两次就换强模型”会把成本花在无效的地方。 Supervisor 的核心智能体现在这张路由表：

| 失败类别 | 处置 | 升级模型是否有效 |
| --- | --- | --- |
| 语法或编译错误 | 附带报错片段，同级模型重试 | 无效 |
| 测试失败且信息充分 | 附带日志尾部重试 | 通常无效 |
| 方向错误、误读契约 | 升级模型 | 有效 |
| 契约物理上不可行 | 架构角色修订契约 | 无效 |
| 环境漂移、认证过期 | 修复环境、重启进程 | **无效，会导致持续消耗** |
| 需求自相矛盾 | 转人工 | 无效 |

**升级先按失败类别路由**。仅模型可修复的任务错误走“附证据重试 → 更换策略 → 强模型修复”；环境/认证问题直接进入环境修复，契约矛盾直接进入规范提案，副作用结果未知直接进入核对。统一的预算上限不能被换模型或切类别重置。

**重试必须包含变化**。以相同提示词重跑是已知低效的做法。每次重试注入失败证据、Supervisor 保存的差异摘要与显式收敛约束（例如“上次修改了 6 个文件，本次限制在 2 个以内”）。Attempt 的恢复点由 Supervisor 固定到 `refs/orgy/attempts/<task>/<n>`，复用同一 Task 目录，不要求 Worker 自己提交或每次新建分支。合并队列失败还需附带前驱候选、完整验证收据与交互诊断，不能仅凭队列位置认定模型方向错误。

**预算与熔断**。Task、集成组与 DAG 都有调用次数、活动耗时及总等待期限；修复轮、被杀 Attempt、诊断和验证重跑均计入相应预算。启动前预留额度，结果出来后结算；超限暂停派发并给出下一步，不自动以更贵模型绕过额度。token 数据缺失时不能声称硬性限制 token 成本，以调用数/时间为硬上限，token 估算仅用于观测。等待人类期间释放物理资源，但不无限延长任务期限。

### 4.3 典型闭环

1. **需求对齐与切片**：人类输入需求 → AI 提案写入 `drafts/` → 人类在 `spec/` 采纳/修改并 apply → 发布不可变版本 → 派发切片。
2. **并行开发**：核心构建与测试工具在固定 Task 工作区并发执行（受写集与资源互斥约束）。进程卡死时终止并采集现场，再走 `one_for_one`；发现契约摩擦则挂起并唤醒架构角色；规范变更按规范和源码依赖证据重派受影响任务。
3. **集成验证与失败升级**：单任务或显式集成组形成候选后进入队列，按目标规范运行完整验收；接口迁移不得拆成无法独立通过的接受步骤。失败保留已接受前缀，按 §3.5 诊断与 §4.2 分类处置。
4. **审查与微检查点**：条件触发审查 → 基线未变且验证有效时按队列顺序晋升精确候选 → 展示阶段成果，等待人类确认方向或修改假设。检查点只提供三个动作：**接受方向 / 修改假设 / 中止重规划**。

## 5. 非目标

- **不内置任何大模型 SDK 或 API 客户端**：完全复用用户本地已配置登录态与环境的 CLI 工具。
- **不限制规范编辑器**：人类直接编辑 Markdown/YAML 并 apply；运行态使用标准 SQLite，可查询并导出 JSON/审计文本，不要求高频机器状态也能手工编辑。
- **不追求无人值守**：坚持微检查点与假设账本，将人类保留在关键决策回路上。
- **不自研终端模拟器，不承诺运行中接管**：PTY 仅用于诊断与人工处理，且“接管”是重新拉起而非附着（§3.1）。
- **不依赖表象层做正确性判断**：这是 §2.3 的直接推论，也是本架构不把终端输出或事件名当作状态来源的依据。
- **不做多用户、跨主机或多 Supervisor 协作**：不实现分布式锁、fencing token、共享状态数据库或远程 Worker 调度；本机多设备由一个 Supervisor 管理。
- **不自研基础设施**：不实现下载服务、包仓库出口代理、Overlay/CoW 层、系统调用级访问审计或自定义日志存储引擎；验证不强制跨平台只读挂载。
- **不做投机合并列车与恶意代码对抗平台**：默认串行验收、可信本地脚本与终态对账；更强隔离只复用用户已有能力，不把其成本放进个人项目首版。

## 6. 实施路线与验收指标

### 6.1 引擎里程碑

- **M0 本地单任务闭环**：Windows、一个 CLI 适配器、固定 Task 路径、OS 单实例锁、SQLite WAL、直接编辑规范与 apply、一个验收计划、Job 回收和 Git 快照。采用全量检查、独立候选副本和终态对账，不实现增量缓存、PTY 或多平台后端。
- **M1 依赖与恢复**：`BLOCKED` 依赖申请、helper 预取、离线验收、数据库/外部操作对账、AI 提案目录、预算和诊断。需要硬件时加入本地占用表与授权命令入口。
- **M2 并行开发、串行集成**：写集调度、显式有界集成组、`parent_tree_commit` 对账与三方迁移；一组一次完整验收，保留失败证据。
- **M3 有收益再优化**：语义哈希与说明文本分离、依赖闭包、可选局部文件集复用；优先测量成本，快的局部检查直接重跑。

### 6.2 增量重算分期

依赖图只服务于减少无效模型调用与重复检查，不重建通用构建系统。分期以个人项目实测成本为准：

| 阶段 | 内容 | 代码量级 | 值得引入的条件 |
| --- | --- | --- | --- |
| **S1** | 条目化 + 规范有效哈希 + 保守源码快照 + 线性失效 + 一律重验 | 小 | M0 正确性闭环稳定后引入，默认禁用接口级截断 |
| **S2** | 正向闭包、拓扑序、“先重验后重写” | 中 | 并行任务达到三个以上，级联开始成为瓶颈 |
| **S3（可选）** | 普通复制的局部文件集 + 明确工具环境 + 检查结果复用 | 小至中 | 重复局部检查确实昂贵且可收窄读取边界；否则直接重跑，无系统调用审计 |
| **S4（可选）** | 字面指纹提示 + 周期性干净重验 | 小 | 用于排查遗漏，不把扫描当作依赖完整证明 |

判断原则可以直接量化：**若一次全量重验只需数分钟，而维护依赖图的成本是数周，则先做全量重验**。增量优化必须建立在完整输入证据上，验证器提供验收证据；二者都不应被解释为对任意运行行为的证明。

### 6.3 验收指标

“高鲁棒”必须可度量，否则无法验收。建议跟踪：

- `CLAIM_MISMATCH` 率（声明产物与实物不符）与 `VALIDATION_FAILED` 率（验收不通过）分别统计；
- `KILLED` 误杀率（被终止后经确认实际仍在正常工作的比例）；
- `PROTOCOL_ANOMALY` 率；
- 每任务平均尝试次数；
- 每任务人工干预次数；
- 合并冲突次数。

此外用故障注入和场景验收覆盖：

- 误启动第二个 Supervisor 只能连接现有实例或退出；人类未 apply 的编辑不影响任务，apply 捕获期间变化不能半批发布，AI 不覆盖规范工作副本。
- SQLite 事务提交、进程启动与 Git CAS 前后强杀进程，恢复后不重复启动/晋升、不丢失已提交动作意图；审计导出丢失不影响数据库恢复，数据库损坏不得从空状态继续。
- 正常退出的澄清、只读审查和合法空 diff 可路由；超时、协议修复、诊断重启不能绕过预算。
- 改目标/验收计划必须失效，数字与字符串不误合并；自身修改不造成自失效，无关源码合入不使全体 Worker 重启。
- 新依赖必须经 `BLOCKED → 准备 → 下一 Attempt` 后自检；缺缓存回到 helper，重复申请有界。离线参数不作为脚本断网证明，正式验收检查实际网络策略。
- B 的父树包含 A 候选时只对账 B 增量；A 更新后 B 可三方迁移并重验，冲突才唤醒模型，组装不重复加入 A 的差异。
- 单改 rationale 不使旧代码收据失效；改正式约束须失效。原稿用于生成代码时，其字节修改仍触发相应重验。
- 同板别名不能并发，未知设备状态不自动重试；验证器无模型/推送凭证。默认终态检查须检测遗留源码变化，并用“改后恢复”反例确认文档未夸大保证；`protected` 模式另测写阻断。
- 抢占后无交付物仍可采集恢复、固定路径续接失败可降级、只读角色可写临时状态；代码实现变化仍执行完整集成，验证结束无存活孙进程。

指标按工具故障、任务失败、输入失效与取消分组，不能将一次规范变更造成的主动终止计为模型失败，也不能通过排除被杀调用来美化总成本。

## 7. 已定默认值与待决问题

默认设计已确定：单用户、单机、单 Supervisor；人类编辑 `spec/` 并 apply，AI 写提案；SQLite WAL 为运行态事实源；依赖预取后离线构建；独立候选副本和终态检查；并行开发、串行验收；必要时使用小型集成组。

仍需实测或进一步设计的事项：

1. **工具适配**：当前 CLI 的交付/续接参数、临时目录、子工具网络限制与 Windows Job 兼容性。
2. **包管理器差异**：预取命令、离线缺包、私有 registry、缓存原生锁与必须运行的构建脚本；优先使用现成能力。
3. **本机验证方式**：默认终态检查的项目假设，现有沙箱断网方式，以及何时需要现成的 `protected` 模式。
4. **个人项目参数**：单任务预算、组大小、局部检查是否值得复用、设备复位与手工接管方式。
5. **备份与清理**：SQLite 备份频率、Git/恢复文件保留期及停机清理命令；不建设通用存储 GC。

## 8. 首轮外部 Review 处理记录（0.2.0）

以下仅保留 **0.2.0 当时的审查记录，不是当前实现要求**。其中代理出口、缓存服务、跨实例协调与投机队列已在 0.3.0 撤销；最新设计以 §1—§7 和 §10 为准。

| Review 项 | 判断与修订理由 | 落点 |
| --- | --- | --- |
| 一-1：软中断要求 CLI 交付 | **采纳核心意见**。信号不能承载任意结构化总结协议；由 Supervisor 终止并采集磁盘现场。允许工具已支持的短暂退出清理，但不依赖模型产出，日志尾部仅作线索。 | §2.1、§3.2、§3.3 |
| 一-2：Attempt 路径与续接冲突 | **采纳固定 Task 路径，修正绝对化前提**。CWD 依赖因工具而异；固定路径加能力探针才能支持续接。Attempt 串行、Supervisor 快照 refs、reset 前保全现场，避免分支重复检出与未跟踪文件残留。 | §2.1、§3.4、§3.5、§4.2 |
| 一-3：隐式源码依赖 | **采纳并补足边界**。注入清单只证明规范依赖；增加源码证据、会话历史读集与保守回退。Sparse Checkout 和普通文件访问日志本身不构成完整隔离或审计证明；不采用“99% 不会截断”这种未经测量的比例。 | INV-5、§3.4、§3.6.4、§3.6.9 |
| 二-1：`output_digest` 自相矛盾 | **采纳拆分，收紧截断条件**。使用 `writes.public/private` 与两个字节级摘要，不承诺 AST/ABI 等价；公开文件不变只允许有读取证据的局部复用，不能豁免实现相关测试或完整集成。另修正示例：`T-4` 注入的 `IF-3` 有效哈希变化时也直接失效。 | §3.6.2—§3.6.7 |
| 二-2：批量 staging 归因 | **采纳合并队列，不采纳“100% 单任务归因”**。队列定位失败增量，交互错误、环境漂移与偶发测试仍需诊断；按精确候选晋升，前驱失败使后续投机结果作废。 | §3.5、§4.3 |
| 二-3：共享配置路径锁 | **采纳方案 A 为默认，方案 B 改为受控集成任务**。锁不能同步旧基线，但 Git 冲突并非必然发生；构建清单与锁文件由 Supervisor 统一修改。包管理器不是天然确定性转换器，必须记录锁定结果；不对运行中的 Worker 自动 rebase。 | INV-6、§3.2、§3.5 |
| 二-4：硬件与环境资源 | **采纳**。引入 `resources` 与统一租约，覆盖 Worker 和验证器；补充设备别名、同板串口/JTAG 联动、复位和跨实例协调，资源锁不替代副作用授权。 | INV-6、§3.5、§3.6.2 |
| 三-1：域名白名单落地 | **采纳代理出口，修正网络前提**。代理变量本身无隔离力，完全断网也无法到达代理，必须有唯一受限通道并阻断直连。HTTPS 隧道目的地过滤不等于内容审计，模型推理连接也需显式授权。 | 架构图、§3.4 |
| 三-2：只读角色临时写入 | **采纳并区分生命周期**。代码库只读，临时区/outbox 按 Attempt 隔离，续接所需状态按 Task 保留；完成收集后清理，不能每次退出销毁全部 Session。 | INV-2、§3.1、§3.4 |
| 四-1：构建缓存 | **采纳**。独立构建输出加受控内容缓存；不假设包管理器缓存目录天然只读或只追加，锁与可写元数据隔离，CoW 克隆作为可选优化。 | §3.4、§7 |
| 四-2：无 schema 交付 | **采纳**。授权 outbox 或带本次 nonce 的唯一完整封装，不要求 stdout 全为 JSON；仍需限长、身份/schema 校验、修复轮与客观验证。 | §3.1、§3.2、§7 |
| 四-3：验证命令与孤儿进程 | **采纳并补足进程边界**。参数数组、允许命令、超时、空 stdin、每条命令完整进程回收；Unix 进程组本身不能阻止脱离会话。幂等性另靠可重建工作区与 fixture 复位保证。 | INV-7/8、§3.2、§3.5、§6.3 |

## 10. 个人项目收缩与本轮 Review（0.3.0）

本轮以单用户、单机、一个 Supervisor 为范围。保留进程回收、输入版本、客观验收与外部动作对账，删除不服务当前规模的基础设施。以下逐项对应 reviewer 的 4 条机制意见和 4 条瘦身建议。

| 意见 | 判断 | 原因、后果与本次修订 |
| --- | --- | --- |
| 一-1：依赖申请与局部自检死锁 | **采纳方案 A，调整预算口径** | 交付后才处理新库，当前 Attempt 确实无法一边申请一边假定编译通过。现在用 `BLOCKED + requested_dependencies` 退出，helper 锁定/预取并准备普通目录依赖快照，再续接下一 Attempt。依赖阻塞不计模型失败，但所有调用计总预算。暂不采用方案 B，避免把任意 manifest 修改反解析成依赖请求而漏掉非依赖语义（§3.2、§3.5）。 |
| 一-2：人类 spec、AI drafts 与显式 apply | **采纳，保留捕获校验** | 个人项目不应把人类直接改规范当作越权。恢复 `spec/` 的直接编辑，AI 提案进 `drafts/`；取消后台 watcher，apply 发布不可变 Git 版本，运行期只读该版本。无 watcher 不等于绝无竞态：apply 时若仍保存文件，需检测变化并重试；不改用户索引或回写文件（INV-1、§3.3）。 |
| 一-3：原稿可读与语义投影冲突 | **采纳上下文可读，不采纳关键词证明** | 默认 worktree 的原稿确实存在，隐藏 rationale 会丢失有用解释。改为保留全文上下文摘要用于溯源，以语义字段决定正式要求；纯说明编辑不自动推翻已通过代码验收。但“没有必须/禁止”不能证明没有新要求，用户需把意图落为条目。原稿若被构建/测试实际消费，仍按字节失效（INV-5/10、§3.6.4—§3.6.8）。 |
| 一-4：集成组下游对账基线错误 | **采纳独立父树与三方迁移** | B 的快照已含 A 的改动，拿 S0 对账会误报越界，组装还可能重复套用 A。每次记录 `parent_tree_commit`，只比较父树到自身快照；上游更新后以旧父树/自身快照/新父树三方迁移，再对账重验。成功不重派模型，失败才修复；不直接 rebase 活跃 worktree 或改写旧证据（§3.5）。 |
| 二-1：预取 + 离线替代缓存与代理服务 | **采纳瘦身，修正离线假设** | 删除自研下载服务、原子缓存发布、Overlay/CoW 与内置包仓库代理；用包管理器普通缓存及原生锁，helper 联网预取，构建锁定版本并离线。但离线仍会写缓存锁/元数据，`frozen-lockfile` 不必然断网，也没有通用 `npm fetch`。脚本断网靠现有执行策略；模型 CLI 连接必须保留（§3.4、§3.5）。 |
| 二-2：删除完整文件访问审计 | **采纳删除，收紧“编过即证明”** | 局部复用不足以支撑自研内核追踪的维护成本。只保留全量重验与可选临时文件集检查；默认复制，硬链接可能改动原件。临时目录仍可能通过绝对路径、链接、搜索环境或旧缓存读外部文件，须明确环境并限制读取，否则关闭复用。一次编译通过不证明 Worker 未依赖其他源码，完整集成不跳过（§3.6.4、§6.2）。 |
| 二-3：SQLite WAL 替代自研存储 | **采纳，限定事务边界** | SQLite 负责运行态事务、WAL 恢复和数据库约束，审计 JSONL 仅导出；删去哈希链、派生 state.json、多代检查点及引用计数 GC。但数据库不会原子更新 Git/设备，也不会靠外键保护磁盘文件，更不是所有故障的免责机制；保留外部操作对账、对象存在性核验与一致备份（INV-4、§3.3）。 |
| 二-4：删除分布式与强制只读挂载 | **采纳范围裁剪，不采纳 100% 检测结论** | 单机只保留 OS 实例锁与本地资源占用，不再规划跨主机协调/fencing。默认独立候选副本加前后真实文件清单检查，取消强制只读挂载；它发现不了“修改后又恢复”，Git HEAD/status 也不等于完整输入哈希。明确可信本地脚本前提并记录 `local_checked` 等级，需更强保护时仅复用现成能力，不另造跨平台隔离系统（§1.1、§3.4、§3.5、§5）。 |

额外收缩：代码开发仍可并行，集成始终串行，不保留投机合并列车；硬件授权只是 Supervisor 内的本地命令入口，不建设远程 broker 服务。原草案版本更新为 `0.3.0`。
